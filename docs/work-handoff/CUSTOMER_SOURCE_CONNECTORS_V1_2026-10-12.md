# Customer source connectors v1 — 2026-10-12

Status: candidate contract on draft PR #36. Default off. No production tenant, provider credential, real booking, or OwlNest open/close is authorized by this document.

The OS workspace, property, room and booking UUIDs are canonical. LINE/Gmail/OwlNest may request a change only through an owner-approved, provider-scoped grant. `customer-events/v1` is a receipt for a change already written and read back; it is not a mutation endpoint. A website quote is not an external inventory hold. Provider result `unknown` remains a durable stop-sale state until reconciled.

## Owner connection

The connector starts a browser-bound authorization flow with a random `state`, a random PKCE verifier and an S256 challenge. It directs the owner to `/w/{slug}/integrations?client_id=…&provider=…&state=…&code_challenge=…`. The logged-in, email-verified owner chooses a property. `POST /api/customer-workspaces/{slug}/integrations` with `action:"issue"`, `propertyId`, `clientId`, `provider`, `state`, `codeChallenge`, `requestKey`, and the current workspace `version` returns only a short-lived redirect to the configured connector URI with `code` and unchanged `state`. OS derives account/workspace/property from the session. No caller-supplied redirect or tenant identity is trusted. The one-time code expires in five minutes.

`POST /api/integration/customer-sources/v1/setup` with a dedicated service Bearer credential and `{action:"exchange",code,codeVerifier,requestKey}` consumes the code, validates S256, current ownership and client/provider scope, and returns `grantId`, `grantToken`, `grantVersion`, `workspaceId`, `propertyId`, `provider`. Same-key retry returns the same result; a different key cannot redeem it. The connector stores the grant token server-side only. Provider OAuth tokens, OwlNest credentials and LINE pairing secrets stay in the connector's secret store, never in OS, URL parameters, browser storage or chat.

The connector then proposes its verified `sourceAccount` and safe display label through the grant endpoint. The OS owner sees the exact proposed account and approves it once before the grant becomes active. Owner `revoke` invalidates future reads/writes immediately. Every machine operation rechecks active grant, matching source account, owner membership, property and grant version; its scope cannot grow silently. Source account change requires a new owner approval. Pending and revoked grants do not enable sales.

## Source bookings and inventory

`POST /api/integration/customer-sources/v1/bookings` uses grant Bearer authentication and a stable `requestKey`/`eventId`, `externalOrderId`, `sourceVersion`, `previousSourceVersion`, `guestName` (verified name or null), expected workspace version, canonical room IDs and stay dates. It atomically upserts/cancels the source order under workspace CAS, binds provider+account+external ID to exactly one OS booking, and returns canonical order ID/version, name, rooms, dates, workspace version and verified status after readback. Same-key retry returns the same result. An uncertain response is queried by same key; no caller may invent a second booking key to recover. A conflicting external source update quarantines the property and prevents website sales until reconciled.

The connector first reads `GET /api/integration/customer-sources/v1/bookings?grant_id=…&grant_version=…&source_account=…&external_order_id=…` with the grant token. It returns an authoritative source-link `exists`, `sourceVersion`, latest applied `requestKey`, canonical order ID/version, current check-in/out and room IDs, workspace version, or explicit absence. A cancellation-before-create tombstone retains its requested room-nights. `diverged:true` means the OS order changed since the last source event; a source write then fails rather than overwriting that edit. This read is advisory under concurrency; the POST's expected workspace and previous source versions are the actual atomic check. `GET` with `request_key` instead retrieves the immutable result of a particular write.

An out-of-order cancellation with no known booking creates a durable source-version tombstone (`orderId:null`, `orderVersion:0`) rather than a booking. An older create with `previousSourceVersion:null` then fails. The response separates the applied event fields from `current` booking state, so historical receipts cannot be mistaken for the latest source version. The connector must namespace `externalOrderId` by the actual OTA provider and must derive a stable source version from provider evidence; an email timestamp alone is not a booking version. This endpoint is not a Gmail inbox reader and cannot prove an email represents a real reservation.

The candidate simple-stay amendment contract is narrower than a generic source upsert. A Gmail create may include `providerRevision` only with a `gmail-evidence-v1:<64-hex>` semantic source version; that establishes `simpleStayUpdateVersion:1` on a single active OS order with a verified guest and no entered money. A later update uses the same `kind:"upsert"` base request plus **all five** fields `previousProviderRevision`, `providerRevision`, `expectedOrderId`, `expectedOrderVersion`, `simpleStayUpdateVersion:1`; `guestName` must be `null` because the OS preserves the original verified name. The grant/account/external ID, previous source version, prior provider revision, exact order ID/version and expected workspace version are checked before one CAS replaces the dates and physical rooms. The new source version must be a new `gmail-evidence-v1` semantic digest; immutable per-order evidence and provider-revision keys prevent an older digest or revision from being applied again after a later revision. The response/readback reports the applied provider revision and capability. Missing update fields are `INVALID_INPUT` (400); stale or replayed source evidence/revision is `SOURCE_VERSION_CONFLICT` (409); a mismatched/cancelled/financially edited order is `SOURCE_UPDATE_CONFLICT` (409); generic Gmail upsert over an existing order is `SOURCE_UPDATE_CONTRACT_REQUIRED` (409); a sold destination is `ROOM_CONFLICT` (409) and leaves the original booking intact. A cancellation-before-create tombstone cannot be revived. PR #89's current create adapter does **not** send an authenticated provider revision, so its current orders continue to read `simpleStayUpdateVersion:null` and its update preflight remains review-only. The `gmail-evidence-v1` source version is the connector's semantic evidence digest; its separate local event journal digest is not sent to this OS endpoint. These digest/revision checks prevent replay and lost-update writes, but the OS cannot itself authenticate the OTA email or prove the provider's revision semantics. Until a real current provider template, sender authority and revision evidence are validated, the connector must leave automatic amendments OFF and send them to review.

`GET /api/integration/customer-sources/v1/inventory` with `grant_id`, `grant_version`, `property_id`, `room_id`, and `date` gives a scoped current OS night read (`bookingOccupied`, `manuallyBlocked`, fences, `canOpen`, workspace version). Each fence includes the **persisted evidence for that exact night and current grant** or `null`; a replacement account sees an older fence as a blocker but cannot read its proof. `canOpen` means only that OS has no known blocker; it is not OwlNest stock or permission to sell. `POST` `acquire_guard` atomically validates the active grant, expected workspace version and exact room-nights, then writes a durable `integration-pending` fence occupying those nights before any OwlNest open. `record_verified` now requires a stable `nightOperationKey` and exactly one provider-readback cell. It atomically persists that cell and advances both the workspace and operation receipt version. Same-key/same-evidence replay returns the original proof; a different key or proof for that night is rejected. The response and `GET` by `operation_key` include sorted `evidence` rows (`roomId`, `date`, `count`, `isLock`, `observedAt`, `sourceVersion`, `nightOperationKey`, `recordedWorkspaceVersion`, `evidenceHash`) plus explicit `missingCells`, `verifiedCells`, `expectedCells`, `readyToFinalize`, and `fenceBlocksSales`. Missing even one night leaves the pending fence and stop-sale in place. The separate `finalize_guard` requires valid evidence for every room-night, a fresh full provider readback that agrees with each recorded cell, and a new OS occupancy/conflict check under workspace CAS. A close becomes a persistent OS block. Reopening removes a block only at that final step **and only under the same grant that created the closed fence**; a new OwlNest account cannot reuse the former account's close proof. Neither a partial readback nor an old operation receipt means a night is currently sellable. The OwlNest transport must use the latest returned `workspaceVersion` for the next write; the old count-only response is insufficient for release.

## LINE owner actions

The LINE command adapter uses its owner-approved LINE grant token at `POST /api/integration/customer-sources/v1/owner-actions`. Each body has `action` and `grant` with `account_id`, `grant_id`, `grant_version`, `channel_id` (verified OA destination U-ID), `user_id` (approved private owner U-ID), `workspace_id`, `property_id`, and current `property_name`; OS validates every field against the active grant and current owner membership. `list` returns only bookings created through this grant's native LINE-owner command path, plus `unavailable_count` for other property bookings that must be viewed in OS. `inspect` takes `order_id` and returns a complete snapshot only when name, phone, count, dates, rooms, total, received and note can be verified. It never fills missing imported amounts with zero.

`preview` takes the command engine's exact `draft` (`action:create|update|cancel`, UUID `request_key`, `order_id` or null, `expected_order_version`, allowlisted `changes`) and creates no booking. It returns `verified`, three-part scope, immutable `before`/`after` snapshots, token, UTC expiry, workspace and order versions and refund-review allowance. `commit` accepts only the original `preview_token`, SHA-256 of the complete canonical sorted UTF-8 preview JSON, request key and expected versions. The token lasts ten minutes; the request key and applied receipt are durable. `status` distinguishes authoritative `not_found`, `rejected` and `committed`; a committed receipt includes the original preview hash and applied versions. A same-key retry reads the same booking. These OS-native LINE actions never claim OwlNest closure or send a guest notification. A paid cancellation marks refund review and preserves the receipt ledger; it does not issue a refund. An owner/admin may subsequently record an actual refund against that cancelled LINE booking in OS; no new receipt or price change is allowed after cancellation.

## Release gates

New integrations require `CUSTOMER_SOURCES_ENABLED=true`, dedicated client allowlist and token secret. The first setup-code exchange disables any existing website binding for that property and sets `pending_verification`; the website binding cannot be re-enabled while a source connection exists. A native OS booking does not by itself authorize public sale. The connector still needs provider OAuth/pairing, source-account approval, two-tenant isolation, duplicate/retry, last-room concurrency, OTA sold-night, revoke, unknown provider result and real owner readback. The existing Happy House credentials must not be reused for 愉園 or 蘭城.

Before any real OwlNest open, the provider adapter must prove a stable property and room/night identity, authenticated provider DOM/API readback for **every** requested night, and an exact room mapping signed off by the owner. A submitted count or `isLock` value from a client is not this proof. Before any real Gmail ingest, the adapter needs an authoritative OS read of the current provider/account/external-order link and a provider-derived event ordering rule; a generic inbound email must not create a confirmed booking. No production credential, customer grant, OwlNest mutation, real booking or deployment is included in this candidate.
