# 每館自行設定入住提醒收件人 — 候選版本 2026-10-12

這是 OS-04 的**新候選功能**，目前只完成程式與本機驗證，尚未發布。10/11 已上線的 Sweetfun／OFFLAND 收件人仍由伺服器設定，兩館既有每日提醒不受此候選功能影響。

## 老闆與管家的操作

1. 老闆先在「旅宿與協作設定」邀請管家，指定該管家可使用的旅宿。
2. 老闆到該旅宿的「入住提醒設定」選擇最多三位已啟用的業主／管理員／管家，可開關每日提醒與「房晚待核對」摘要。這一步只保存設定，尚未配對 LINE 的成員不會收到訊息。
3. 每位被選定的成員用自己的 OS 帳號登入同一頁，各自產生 10 分鐘有效的一次性「接收入住」指令，再用自己的 LINE 帳號一對一私訊民宿小幫手。同館不可把同一 LINE 帳號配給兩位成員。LINE webhook 必須驗證官方簽章及一對一來源，OS 只接受 webhook 提供的真實 userId；瀏覽器不能自行填入任意 LINE ID。
4. 成員回到後台重新查詢，確認「已配對」。若老闆移除成員，舊 LINE 配對立即失效；取消該成員的旅宿權限或關閉提醒，停止新的發送。已開始的發送仍可完成回條，未知結果不自動重送。

每館目前支援**最多三位**收件人，可更換，每位配對後各收一則。功能由新的旅宿後台設定啟用；原 Sweetfun／OFFLAND 的既有收件人仍使用獨立的受信任伺服器設定。首次啟用需要 OS 與 LINE 兩端候選版本一起發布；單獨發布其中一端不構成可用的管家配對。

## 通知內容

現有 `reminderText` 是真實模板，後台提供不含真實客資的預覽。僅對今日／明日**已確認入住、有備註、尚未標記已處理**的訂單發送。每筆訊息包含館名、「今日／明日入住備註」、客人姓名、房間、入住與退房日期、原備註、訂單連結，以及「送達不代表已處理」提示。備註若超長，LINE 截短並提示到 OS 查看全文。當日沒有符合條件的訂單，不會發空白提醒。

勾選「房晚待核對」時，若來源提供未核定房晚，另發明確標示的每日摘要及後台連結；不將可能續住的房晚宣稱為新入住，不附無法核定的姓名或備註。來源無法安全核對時維持拒絕發送，不能用空訊息假裝資料完整。

## 權限與持久化

OS 狀態保存在每個 workspace／property 的 Redis 記錄，並以 CAS 原子維護獨立 target 索引。只有該旅宿 owner 能選人與開關；只有被選中的成員能從本人登入工作階段申請配對。LINE 端使用現有獨立 arrival worker capability 消費配對指令，並在每次發送前重新核對成員仍啟用且具該館權限、旅宿 owner 仍有效及收件人已配對。每館預留三個固定 target 槽位；同筆訂單對各已配對收件人各有獨立防重回條與 provider receipt，移除收件人後仍可 ACK 進行中的發送。舊館原有跨 binding 的 per-property／order／day 防重不變。若當日更換人選，槽位可能沿用已送達的訂單回條，新成員從下一個每日週期完整接收。

候選上限為 16 間動態旅宿、每館三個固定 target，即最多 48 個動態 target；與現有兩個舊館 target 合計不超過 50。超過上限時明確拒絕新增，不能靜默漏發。擴至更多旅宿或單館大量入住備註需先調整 discovery 分頁與發送容量。2026-10-12 已向先前驗證的業主 LINE 帳號送達一則明確標示為「內容預覽｜虛構資料」的範例，送達與防重稽核均核對；這不是三位實際管家配對或正式排程驗收。候選功能尚未部署。
