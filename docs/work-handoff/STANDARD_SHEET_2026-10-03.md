## 最新產品決定

2026-10-03，業主要求先規劃，再直接實作，不另設計畫審核關卡。

- 客戶保留原始 Google Sheet，不改欄位、不合併來源列、不回寫。
- 不要求申請信箱與 Sheet 建立者、擁有者、編輯者相同，也不查這些人的權限。客戶提供連結，系統可以讀取即可進入格式對應。工作區登入、成員角色及館別隔離仍照常運作。
- 建立我們自己的標準 Google Sheet 格式，以及可重跑的轉換程式。
- 一張訂單有多個住宿明細與多筆收付款。多房、多晚、不同日期共用訂單總額與訂金，不能把金額複製後加總。
- 不在開通流程普遍詢問「已付給民宿還是平台」。預設保留來源已付摘要，不把它直接稱為民宿銀行實收，也不捏造交易日期。舊有已明確指定的實收／旅客已付資料保留原語意。

本文件取代先前客戶導入文件中「信箱須為 Sheet 擁有者／編輯者」與「匯入僅接受一列完整訂單」的規定。既有原始旅宿 Sheet 與舊系統同步器不在本次改寫範圍。

## 實作計畫

1. **記錄規格**：固定標準帳本欄位、來源關聯、日期與金額規則、錯誤處理及同步方向。
2. **轉換核心**：支援整筆訂單列、房間／日期區間列、一房一晚列、日期橫排的房況格。使用明確訂單編號或逐筆指定的分組；不能用客人同名推定同一訂單。
3. **匯入整合**：預覽以整張訂單為單位，顯示來源列、房晚數、合併後總額與待處理原因。確認與重試沿用版本檢查、衝突檢查及防重複寫入。
4. **標準 Sheet**：建立原生 Google Sheet 範本；程式產生同一格式的訂單、住宿明細、收付款及來源對照。提供受控寫入與讀回驗證，來源與目的地不可相同。
5. **驗證與交付**：覆蓋多晚、多房、不同日期、重複訂金、未知金額、重複編號歧義、來源變動、重跑、權限隔離及寫入失敗；完成本機檢查與原生 Sheet 讀回。

## 標準帳本

每個工作區的帳本獨立，不把不同客戶的資料放進同一個檔案。每列包含館別識別；完整帳本僅提供給該工作區擁有者。工作區內的其他成員繼續透過具館別及金額權限限制的產品介面存取。

| 分頁 | 一列的意義 | 關係 |
| --- | --- | --- |
| 訂單 | 一張訂單 | 訂單 ID 是主鍵，總額只記一次 |
| 住宿明細 | 一間房的一個住宿夜 | 訂單 ID 連回訂單；房間與住宿日唯一 |
| 收付款 | 一筆確定交易，或一筆明確標為來源累計的期初摘要 | 累計摘要不當成本期現金收入 |
| 來源對照 | 一個訂單或房晚與來源列／儲存格的關係 | 可從標準資料追查原始資料 |
| 轉換規則 | 一條版本化轉換規則 | 說明日期、分組、金額及例外 |
| 系統設定 | 結構版本、帳本綁定與同步標記 | 程式辨識與讀回驗證 |

Google Sheet 是可檢視及交換的標準帳本；既有工作區交易儲存繼續負責原子操作與版本控制。本次不把兩個儲存位置宣稱為同一個原子交易，也不暗中切換舊旅宿的最終資料來源。標準帳本寫入若失敗，必須顯示待同步，不能將工作區已成功的付款再次登記。標準 Sheet 不反向修改原始 Sheet。

## 轉換規則

### 訂單與日期

1. 整筆訂單列：讀入住與退房，展開各房間的住宿夜。
2. 房間／日期區間列：同一可靠訂單編號的多列合併成一張訂單，可有不同房間或不連續日期。
3. 一晚一列：住宿日加一天為該列退房日，再按訂單編號合併。來源不必補出退房欄。
4. 房況格：日期欄必須能確定年份，房間必須能對應。格子需含明確訂單編號，或在匯入對應時為每個有內容的格子指定訂單分組；不因顏色、同名、相鄰位置或空白延續而猜測。
5. 入住日包含，退房日不包含。10/10 入住、10/12 退房占用 10/10 與 10/11。
6. 同張訂單中重複占用同一房間同一天，或與另一張有效訂單重疊，列為衝突，不默默去重或覆蓋。
7. 同一來源編號若有矛盾的客人、訂單總額、累計已付等資料，整組待核對，不能只匯入其中幾列。
8. 一筆跨館訂單不自行分攤款項。各館分開建單與明確分攤仍是既有邊界。

### 金額

1. 整筆訂單總額：同組非空金額必須一致；只取一次。
2. 每列金額：相加各列的完整金額，任一必要值缺少時總額維持未知。
3. 每晚金額：乘該列住宿晚數；只有明確指定「每房每晚」才另外乘房間數。
4. 重複的來源累計已付／訂金：同組非空值必須一致，只取一次；不同值不取最大值、不任意相加。
5. 累計金額無付款日期時，只記為來源期初摘要，日期留空；不能建立假的付款交易。
6. 來源沒有逐晚房價時，住宿明細的房價保持空白，不把平均分攤冒充原始房價。
7. 空白是未知，0 是已知零；金額以整數分計算後再顯示，保留兩位小數。
8. 來源內容一律作為文字或數值寫入，不能讓客戶姓名／備註變成 Google Sheet 公式。

### 重跑與追溯

- 訂單分組以來源檔案、分頁、館別及來源訂單編號為範圍，不跨客戶合併。
- 沒有來源訂單編號的整筆訂單可保留獨立身分；多列或房況格資料必須有明確分組。
- 保留來源列／儲存格清單與來源內容指紋。排序不改變同一組的結果；相同預覽重送不新增第二筆訂單或訂金。
- 預覽後來源若變動，重新預覽；不能以舊預覽覆蓋新來源。
- 標準 Sheet 僅允許寫入已綁定的獨立目的帳本；不得把任意使用者傳入的 Sheet 當成可覆寫目的地。

## 範例驗收

兩間房 101、102，10/10 入住、10/12 退房，總額 12,000，累計已付 3,000：必須得到 1 張訂單、4 筆房晚、1 筆來源累計摘要。餘額 9,000 只表示依來源已付計算的訂單未付；不等同已完成銀行／平台對帳。

同一訂單另有 10/20 的住宿時，只新增當天房晚，中間空檔不占房。若來源四列都寫了 12,000 與 3,000，仍只保留總額 12,000、累計已付 3,000。

## 使用與設定

1. 為工作區複製空白標準帳本，保留六個分頁與標題；不要複製示範資料作為新客戶帳本。
2. 僅將目的帳本的編輯權限分享給設定頁顯示的服務帳號。客戶原表仍只需檢視權限。
3. 業主在工作區設定的「標準帳本」連結副本。伺服器檢查標準格式、空白狀態、來源不同於目的地，以及一個帳本只能綁定一個工作區。
4. 訂單／收退款／匯入／撤銷成功後會嘗試更新已綁定帳本。工作區版本較新時顯示待更新，失敗顯示原因，可重新更新並讀回核對；沒有每分鐘保證或另設排程。
5. 直接編輯標準帳本的資料會停止下一次覆寫，以免蓋掉外部修改。先核對修改內容；完整工作區 JSON 可由業主下載保留。標準帳本是輸出，不是直接輸入收款的介面。

環境設定：`CUSTOMER_STANDARD_SHEET_CREDENTIALS` 可使用獨立寫入帳號；未設定時沿用專用的 `CUSTOMER_SHEET_READER_CREDENTIALS`，但只有明確分享成編輯者的目的檔可寫入。`CUSTOMER_STANDARD_SHEET_TEMPLATE_ID` 會禁止把主範本綁成目的檔。自動複製還需 `CUSTOMER_STANDARD_SHEET_FOLDER_ID` 指向可寫的 Google 共用雲端硬碟資料夾；本次已確認連接帳號沒有共用雲端硬碟，因此未啟用自動建檔，也沒有宣稱完成每客戶自動配置。已準備的獨立副本可立即連結。

Google 服務帳號不能靠個人 My Drive 容量擁有新檔案；自動建立使用共用雲端硬碟，或日後另設使用者授權流程。[Google 共用雲端硬碟文件](https://developers.google.com/workspace/drive/api/guides/about-shareddrives)。工作區與 Google Sheet 仍是分開交易；Google 的單次六表批次使用 [Sheets batchUpdate](https://developers.google.com/workspace/sheets/api/reference/rest/v4/spreadsheets/batchUpdate)。

## 程式與重跑驗證

- `sheet-normalizer.ts`：分組、日期與金額規則；`sheet-import.ts`：預覽、整組匯入、來源／版本檢查、防重複與撤銷。
- `standard-sheet-schema.ts`／`standard-sheet.ts`：版本 1 六表結構、26 條規則、房晚與收付款輸出、型別值及內容指紋。
- `standard-sheet-google.ts`／`standard-sheet-sync.ts`：Google 原生表格寫入、帳本綁定、單一寫入租約、持久化待輸出版本、失去回覆後復原及完整讀回。
- `/api/customer-workspaces/[slug]/standard-sheet`：僅完整業主可讀取、下載、綁定或同步；沒有價格權限的使用者也收不到每晚房價。
- `frontend/scripts/standard-sheet-example.mjs OUTPUT_DIRECTORY`：用 `node --experimental-strip-types` 執行，以相同預覽／匯入流程產生全合成範例 JSON。無網路、無正式儲存存取。

驗證涵蓋多列金額只取一次、逐晚與不同區段、歧義整組隔離、同名不合併、重複占房、日期／金額型別、文字不執行成公式、角色／館別隔離、失去回覆、讀回不符、競爭寫入、外部編輯、建立結果不確定與重試。HTTP 測試使用真實 Next request/response 與合成 Google/Redis 回覆；沒有寄送測試郵件。

最終本機驗證：83 個客戶服務／元件測試加 4 個 HTTP 整合測試，合計 87 個通過（其中 12 個轉換規則、14 個標準帳本／復原測試）。ESLint 無錯誤，保留兩個原有日曆元件警告；含 TypeScript 的正式 webpack 建置通過。本次未改 Python 後端。真實 Google 寫入與讀回的驗證結果如上，並不等於正式客戶 Redis 或瀏覽器操作驗收。原有瀏覽器政策與正式站切換邊界仍保留。
