# Google Calendar 快速導入規劃

起草於 2026 年 10 月 3 日，最後整理於 10 月 4 日。狀態：歷史設計稿；10 月 4 日已實作三種入口與共用後端，最新能力、差異與驗證邊界以 [實作與審查紀錄](CALENDAR_ONBOARDING_2026-10-04.md) 為準。

本規劃讓用 Google Calendar 記訂單的民宿，直接把日曆轉成可核對的訂單與房況，再接到既有標準帳本。開通入口同時納入 Google Sheet、Google Calendar、iPhone／iPad 日曆、Android 手機日曆及其他來源。iOS 與 Android 的專屬導入列入待辦，本次先定義 Google 路徑。

使用者已確定上述客群與規劃優先序。以下預設區間、分期、同步頻率與效能指標是本次設計建議，不是已上線能力或已驗證的服務承諾。以下保留原設計；後續使用者已要求實作。不能把未完成的規劃項目誤認為既有能力，也不能把本稿原先的「尚未實作」當作最新狀態。

共同流程是「選來源 → 連結或上傳 → 確認房間與日期 → 預覽及處理例外 → 保存並核對」。實作先完成來源共用基礎與 ICS／ZIP 匯入，再接 Google 唯讀授權，最後開放持續單向同步。

## 開通入口與日曆來源

第一題用客戶熟悉的名稱：「你現在用什麼記訂單？」支援複選，保存每個館別所有尚未處理的來源。不得因第一個來源匯入完成，就把其他未處理來源當作空房。

| 客戶選項 | 後續分流 | 本次狀態 |
| --- | --- | --- |
| Google Sheet | 貼來源連結，沿用既有格式對應 | 已有功能，保留 |
| Google Calendar | 連結 Google，或上傳日曆檔 | 本次詳細規劃 |
| iPhone／iPad 日曆 | 先辨識該日曆所屬的 Google、iCloud、其他帳號或裝置來源 | 已排入待辦 |
| Android 手機日曆 | 先辨識 Google、Exchange、廠商帳號或僅存手機 | 已排入待辦 |
| 其他／不確定 | 提供來源辨識引導與協助入口，可保存進度 | 保留擴充入口 |

App 名稱與資料來源分開保存。Apple 日曆可使用多種帳號；Android Calendar Provider 也有不同帳號及不會同步的本機日曆。因此，iOS／Android 使用者若實際將事件存到 Google，應導入同一條 Google 路徑。不能只因使用 Android 就推定資料在 Google，也不能只因使用 iPhone 就推定資料在 iCloud。[Apple 帳號說明](https://support.apple.com/guide/iphone/change-calendar-settings-iphc37be2016/ios)、[Android Calendar Provider](https://developer.android.com/identity/providers/calendar-provider)。

來源不確定時，引導使用者打開一筆訂單事件，查看它所屬的日曆與帳號；先做這個小步驟，不先要求搬動全部資料。不同 App 若指向同一個 Google 日曆，只建立一個來源綁定。

## Google 的兩種導入方式

| 路徑 | 客戶操作 | 用途與邊界 |
| --- | --- | --- |
| 連結 Google Calendar | 授權唯讀、勾選民宿日曆、確認轉換結果 | 正式自助入口；持續同步完成後可沿用原本日曆工作習慣 |
| 上傳日曆檔 | 上傳 `.ics` 或含多份 `.ics` 的 `.zip`，選擇要導入的日曆 | 最早可交付的一次搬家路徑；上傳檔案本身不代表持續連線 |

Google 官方匯出需在電腦操作，且匯出者需要「變更活動及管理共用設定」權限，組織也可能限制匯出。單一日曆匯出 ICS，批次匯出 ZIP。這是 Google 匯出的產品限制；我們不另核對日曆建立者與系統登入信箱是否相同。[Google 匯出說明](https://support.google.com/calendar/answer/37111?hl=zh-Hant)。

直接連結使用能讀到活動內容的 Google 帳號，支援可讀的共用日曆。只能看到忙碌時段、看不到私人活動細節時，顯示「只能讀取占用時段」，不可宣稱可產生完整訂單。

## 客戶實際經過的流程

1. **選來源與建立工作區**：選 Google Calendar，填旅宿與房間基本資料，沿用信箱驗證及自行設定密碼。已有帳號則登入並選館別；日曆導入不要求 Sheet 連結。Google 授權帳號可以與工作區登入帳號不同。
2. **連結或上傳**：登入工作區後才進行 Google 授權或上傳旅客資料。回到原來步驟並保存進度；授權拒絕或中斷可重試，也可改上傳。不得先要求加入服務帳號或建立標準 Sheet。
3. **選日曆與期間**：只處理使用者勾選的民宿日曆。預設範圍為旅宿時區的今天至未來 12 個月，包含今天仍在住的訂單；可調整。歷史資料可稍後匯入，範圍外顯示「尚未匯入」，不顯示為可售。
4. **確認使用習慣**：用幾筆代表事件確認房間對應、日期語意與標題欄位。常見規則一次設定，套用後再讓使用者查看整體結果；每筆例外仍單獨列出。
5. **預覽與處理例外**：先顯示月曆，再列訂單數、占用房晚、封房數、待確認及排除數。可回到每筆原始事件。金額缺少可先導入；房間、日期或占用衝突必須先處理。
6. **確認導入並讀回**：原子寫入完整訂單組、來源對照及覆蓋狀態，再查詢實際保存結果。重按或網路重試不新增第二張訂單。標準帳本輸出狀態單獨顯示，帳本暫時未建好不阻止訂單預覽與保存。
7. **交代後續在哪裡操作**：清楚顯示目前是「一次匯入，之後在系統操作」或「Google 日曆持續連結」。後者必須在背景同步驗收完成後才開放。

第一次使用的目標是先得到可信的未來房況，財務完整度可以稍後補齊。成功畫面分開呈現「房況已核對」、「款項待補」、「標準帳本待更新」；不能把任一項未完成都模糊寫成開通失敗。

## 最少必要的三組確認

### 日曆與房間的關係

| 原本的使用方式 | 對應規則 |
| --- | --- |
| 一個日曆代表一棟包棟 | 選擇該館與實際占用房間集合 |
| 一個日曆代表一間房 | 每個日曆對應房間，支援批次確認 |
| 多間房寫在同一個日曆 | 從標題或說明辨識房號；列出樣本讓使用者確認規則 |
| 用顏色表示房間或狀態 | 只有來源提供顏色資訊且使用者明確設定意義才使用；匯出檔缺少顏色時要求另一個對應方法 |
| 一筆訂單分成多個活動 | 用明確訂單編號或使用者確認的活動群組合併；同名或相鄰日期都不足以自動合併 |

### 日期的意義

讓使用者選擇「活動涵蓋整段住宿」或「只是入住提醒」，並以實際例子核對。

- 整段住宿：以原始開始／結束資料轉換。Google API 的結束時間不包含在區間內；全日事件的畫面呈現不能直接當作原始退房欄位。例如原始開始 10/10、結束 10/12，是 10/10 與 10/11 兩個占用日。[Google Events 定義](https://developers.google.com/workspace/calendar/api/v3/reference/events)。
- 入住提醒：事件可能只有一小時，必須從明確晚數、退房日期或使用者補充得到住宿區間，不以提醒時長當晚數。
- 以「最後住宿日」記錄的客戶：先讓使用者用樣本確認規則，再換成退房日；不因文字日期與事件日期不一致就自動加一天。
- 跨午夜與有時間的活動：保留原始時區與時間，再依旅宿時區及已確認規則轉換；只做日期截字可能錯一天。ICS 的無時區時間需有來源／使用者確認的時區。
- 重複活動：只展開選定期間；每個發生實例分開追蹤，包含改期與取消例外。不把同一系列當成一張跨整年的訂單。

### 標題和說明的意義

先支援明確標籤及使用者確認的固定格式，例如「101 王小姐 2晚 總額8000 訂金2000」。AI 可提出欄位建議，但每個提取值保留原文片段；日期、房間、分組與金額由確定性規則驗證後才寫入。

- 沒有姓名時可顯示待補，不從活動邀請名單推定住宿旅客或人數。
- 沒有金額時保留未知；單獨出現「2000」或「已付」不能猜成總額或實際收款。
- 同一訂單分成多個房間／活動時，總額及累計訂金只記一次。來源累計不捏造交易日期、不直接當作本期收款。
- 房號、日期、金額相互矛盾時，整組待核對。訂單關鍵資料不靠模型信心分數直接通過。
- 維修、自用與停賣屬封房；清潔提醒是否影響整晚房況需明確設定；私人行程可排除並記錄理由。Google 的「忙碌」或活動回覆狀態本身不等於已確認住宿。

## 日期覆蓋與未知房況

完整度必須以館別、房間、來源、開始日、結束日及最後成功讀取時間表示，不只用一個「匯入完成」。多來源混用時，合併計算所有應納入來源的覆蓋。

已確認的訂單可以先保存，未解決事件影響的房間與日期仍標為未知；若連受影響的房間或日期都無法確定，該館的相關匯入期間維持未知。第一版可先採全館期間阻擋，再細化到房間，不能為追求快開通把無法判讀的活動當空白。

API 分頁未讀完、檔案截斷、超出解析上限或必需來源漏選，都不能宣布覆蓋完整。已在入住中的事件需要按區間相交匯入，不能只篩選開始日期在今天以後的事件。

## 來源身分與重跑

- API 的原始活動以工作區、來源日曆 ID、活動 ID 保存；重複活動另保留系列 ID 及原始發生時間。
- ICS 以已綁定來源、UID 及 RECURRENCE-ID 辨識。檔案更名、排序或 ZIP 路徑改變不應改變同一來源身分。重傳時先選擇更新哪個已存在來源，不能把檔名當唯一身分。
- 來源活動身分與商業訂單分組分開。保留每個來源活動，不因同名直接合單；跨日曆相同 iCalUID 只作為檢查線索，經明確副本規則或使用者確認後才去重，避免吞掉合法的多房資料。
- 從 ICS 改為 API 連結時，先核對來源日曆及 UID／發生實例。無法唯一匹配則待處理，不能重複新增。沒有 UID 的非標準檔可預覽並提示修正，暫不啟用可重跑的正式匯入。
- 保留來源版本、內容指紋、轉換規則版本、預覽版本與工作區版本。API 預覽後重新讀取，資料已變動就更新預覽；ICS 則以不可變上傳快照核對。
- 重傳同一份檔案可去重；修正版先顯示差異。某活動沒有出現在新檔案，不等於客戶已取消訂單。
- 撤銷匯入只處理尚未被修改、記款或其他來源接管的記錄；保留稽核，跳過已有後續操作的訂單，並重新計算日期覆蓋，不刪除已發生的付款。

Google 的 API 活動 ID 與 iCalUID 並不相同，重複活動各實例也有不同 API ID；不能混用為單一主鍵。[Google Events 定義](https://developers.google.com/workspace/calendar/api/v3/reference/events)。

## 持續連結的操作規則

此模式在單向同步完成後才提供。Google 是其綁定訂單的住宿日期、房間及原始客人資料來源；我們的系統保存實際收退款與內部備註。標準 Sheet 仍是工作區的輸出，不回寫 Google。

| 來源變更 | 系統行為 |
| --- | --- |
| 新增可確定的住宿活動 | 沿用已確認規則，驗證占用後新增；歧義進待處理 |
| 改日期、房間或原始客人資料 | 比對來源版本與內部修改記錄，無衝突才更新並讀回；有衝突保留現況及待確認變更 |
| 出現新的金額／訂金文字 | 更新來源證據並列出差異，不自動新增付款或覆寫已確認財務資料 |
| 刪除活動或取消重複活動實例 | 標示來源已刪除／取消，等待使用者確認是否取消住宿；未確認前保留占用，不自動退款 |
| 單次讀取少了一筆 | 先標示來源差異，不把讀取缺漏或期間改變當作取消 |
| 失去授權、來源不可讀或長時間未同步 | 保留既有資料，顯示過期狀態，停止用未知房況宣稱可售 |

為避免單向同步產生兩套住宿排程，連結館別第一版的新訂單與來源訂單改期入口導向 Google，待同步後在系統記錄收款。要改由我們管理住宿，需明確完成一次搬家；新增或修改來源占用的產品操作不得悄悄變成只存本地。雙向回寫另案規劃。

背景工作先採可恢復、分頁完整的有界期間讀取與差異比對。同步範圍就是顯示的覆蓋期間；每次往前延長範圍都重新核對，完成前新增期間屬未知。提議每 5 分鐘排程一次，超過 10 分鐘未成功更新顯示過期；實際頻率須依配額、任務容量與試跑驗證後設定，不宣稱即時或防超賣保證。手動更新使用同一任務與去重機制。

後續效能優化可加增量同步及推播。使用 syncToken 時不能同時帶 timeMin、timeMax、q 等不相容條件；分頁與來源游標需完整提交後才前進。410 代表重建來源快取，不能清空正式訂單或收付款。Google 推播不含事件內容，仍需讀取活動，通知通道也需要續期；不能只接 webhook 就宣稱完成同步。[Events list](https://developers.google.com/workspace/calendar/api/v3/reference/events/list)、[同步說明](https://developers.google.com/workspace/calendar/api/guides/sync)、[推播說明](https://developers.google.com/workspace/calendar/api/guides/push)。

## 既有程式要接上的位置

目前的 Sheet 與標準帳本程式可沿用共用規則，但不能把日曆偽裝成有列號的 Sheet。

| 現有位置 | 已確認現況 | 規劃修改 |
| --- | --- | --- |
| `customer-intake/types.ts`、`service.ts`、`service-join.tsx` | 來源只有 sheet／other／unknown；加入申請要求 Sheet URL 與分享宣告 | 增加來源選項、App 與實際服務分類，來源各自驗證，保存未完成進度 |
| `customer-intake/onboarding.ts` | 開帳與信件內容綁定 Sheet 可讀性 | 來源無關的工作區啟用；Sheet、日曆、檔案分別進入對應導入頁 |
| `customer-workspaces/customer-google.ts` | 既有 OAuth 只讀 Sheets、online token 約一小時，無持續更新授權 | 新增獨立 Calendar 連線模組，沿用 session 綁定、state 與加密原則，不能直接拿 Sheets token 讀 Calendar |
| `customer-workspaces/types.ts` | `setup.mode` 僅 empty／sheet；`entry` 僅 os／sheet；來源對照使用列／格 | 引入帶 kind 的來源描述、日曆原始事件參照、可版本化的導入批次；相容既有 Sheet 記錄 |
| `sheet-normalizer.ts`、`sheet-import.ts` | 已有分組、金額、衝突、防重複及撤銷 | 提取來源無關的訂單驗證／提交核心；Sheet 與 Calendar 各有解析器，不虛構 spreadsheetId 或 row |
| `domain.ts`、`service.ts`、`operations.ts` | 完整度只有起日／總體狀態；新單依此阻擋；尚無獨立封房類型 | 補 coverageTo、來源／房間覆蓋及新鮮度，建立封房模型並納入所有可售查詢與寫入檢查 |
| `standard-sheet.ts`、`standard-sheet-schema.ts` | 六表結構 v1；來源欄位與財務判斷仍含 Sheet 假設 | 版本化新增日曆來源參照與封房輸出，盤點所有 `entry === "sheet"` 財務／去敏判斷；未知金額保持未知 |

建議新增 `calendar-source`、`calendar-normalizer`、`calendar-import`、`calendar-google` 與 `calendar-sync` 模組。所有任務與原始來源參照綁定工作區及館別。匯入權限沿用角色與館別範圍；來源連線設定由完整工作區擁有者管理。

Google 授權採 `calendar.calendarlist.readonly` 與 `calendar.events.readonly`。Google 授權範圍本身不是逐日曆挑選，我們在產品層綁定所選日曆；頁面不得把兩者混為一談。持續連線需離線授權與加密保存 refresh token，處理撤銷、換帳號、重連及移除連線。Google 連線不取代工作區登入，不用 Google email 推定工作區歸屬。[Calendar scopes](https://developers.google.com/workspace/calendar/api/auth)、[OAuth Web Server 流程](https://developers.google.com/identity/protocols/oauth2/web-server)。

首批試跑前確認 Calendar API、OAuth 同意畫面、回呼網域及測試帳號；公開提供前完成適用的 Google 驗證。只盤點需求，不在規劃階段新增正式憑證、擴大現有服務帳號權限或變更原有 Sheet 來源。

## 檔案與原始資料處理

檔案導入處理 UTF-8、折行與跳脫、全日日期、TZID／VTIMEZONE、DURATION、RRULE／RDATE／EXDATE／RECURRENCE-ID 與 STATUS，保留 SEQUENCE 作版本核對。未支援的規則或 THISANDFUTURE 例外需明確列為待處理。選用維護中的 iCalendar 解析套件後用合成案例驗證，不自行用逐行字串切割取代格式解析。[iCalendar 格式規範 RFC 5545](https://www.rfc-editor.org/rfc/rfc5545)。

ICS／ZIP 上傳需設解壓後大小、檔案數及事件展開上限；超限必須顯示尚未完成，不靜默截斷。ZIP 不允許路徑穿越，不讀取遠端附件，不執行描述中的 HTML 或公式。先列出日曆讓客戶選擇，再傳送／保存所選內容；未選日曆不得進入工作區資料。

建議原始上傳與未確認預覽保存 24 小時後清除；已提交訂單只保留核對所需的來源身分、版本、原文證據與稽核資料。原始描述可能含姓名或金額，無價格權限成員不得透過原文旁路取得金額。事件、憑證與真實客戶匯出檔不可放入 Git、分析事件或一般錯誤日誌。

## 分期與完成條件

### G0 共同入口與資料契約

先完成來源選單、保存進度、來源無關的啟用與導入狀態；定義 Calendar 來源、封房、有限日期覆蓋及泛用財務來源。所有新選項須有真實可走的下一步；尚未支援的 iCloud／裝置本機路徑導向說明或協助，不顯示已連結。

### G1 日曆檔一次導入

完成 ICS／ZIP → 日曆選擇 → 房間與日期規則 → 例外 → 訂單／封房保存 → 查詢驗證 → 標準帳本。提供可重傳去重、修正版差異及撤銷。只標示一次匯入，適合願意搬到我們系統的試跑客戶；不適合宣稱仍在 Google 記單也會自動更新。

### G2 Google 唯讀連結與快速預覽

完成連結、日曆選取、共同預覽、來源變動檢查、重連與解除。手機瀏覽器可走完整授權返回流程；資料來源在 Google 的 iOS／Android 使用者共用這條路。此階段可用作一次搬家，持續連結選項尚不對外承諾。

### G3 持續單向同步

完成持久化排程、重試、來源新鮮度、差異處理及兩邊欄位責任。新事件、改期、取消、失去權限與重新授權必須在實際來源完成閉環驗收，才開放「繼續使用 Google 日曆」。同步工作不能只依賴一次 HTTP 請求後的盡力執行。

### G4 iOS 與 Android 專屬快速導入

依下方待辦盤點真實裝置與帳號組合，優先沿用可用的 Google 或 ICS 路徑。iCloud 與僅存手機資料另評估讀取方式；不先建立三套互不相容的訂單轉換核心。

## 驗收案例

| 案例 | 必須看到的結果 |
| --- | --- |
| 同一人用 iPhone 與電腦看同一個 Google 日曆 | 一個來源綁定，不重複匯入 |
| 共用日曆可讀，Google 帳號與系統信箱不同 | 可進入預覽，不增加建立者身分審核 |
| 全日原始區間 10/10 至 10/12，兩間房 | 1 張訂單、4 房晚；總額／訂金各一次 |
| 15:00 至 16:00 入住提醒，未寫晚數 | 待補日期，不推定一晚；相關房況不算已核對 |
| 今天仍在住，入住日是昨天 | 出現在導入與占用中 |
| 同名不同活動、跨日曆副本、多房拆活動 | 不靠姓名去重；副本與分組有可追溯確認 |
| 固定每週活動，單次改期／取消 | 只處理期間內實例，保留系列及例外身分 |
| 金額缺少、訂金重複、幣別不明 | 房況可先保存；金額未知或待核對，不產生假收款 |
| 維修、自用、清潔提醒及私人活動 | 按已確認規則保存封房或排除，不混成營收訂單 |
| ZIP 多日曆、截斷／超限、API 多頁未完成 | 只選取民宿來源；未完整讀取不能宣布房況完整 |
| 重傳更名檔、網路重送、ICS 切 API | 同來源同實例不重複；匹配不唯一必須停在待確認 |
| 預覽後改期、工作區同時新增訂單 | 重新驗證來源和占用；不覆蓋、不重複寫入 |
| 原始來源改金額、刪活動 | 不改真實付款、不自動退款；保留差異與原占用直到確認 |
| 失去授權、背景任務中斷、讀回不符 | 可恢復且有真實狀態，過期房況不能被稱為已核對可售 |
| 多館、跨工作區、無價格權限 | 來源資料與原始描述依館別／金額權限隔離 |
| 標準 Sheet 未綁定或寫入失敗 | 訂單保存結果仍正確；獨立顯示帳本待設定／更新 |

試跑先收集三種實際樣本：每房一日曆、同日曆用標題分房、僅記入住提醒。樣本以最少必要期間提供，實際檔案只放授權的私有測試環境；Git 使用合成替身。這是後續驗收所需素材，不阻止先完成 G0 與合成案例。

追蹤來源選擇到預覽、預覽到首次保存的時間、每百筆需修正數、重複訂單數、日期錯誤數與同步延遲。標準格式客戶 5 分鐘內看到可核對預覽可作為試跑目標，尚無量測結果；不能寫成產品保證。

## 手機日曆待辦

- [ ] iOS：辨識 Google、iCloud、Exchange／其他及裝置來源；不知道帳號時提供從事件查看所屬日曆的引導。
- [ ] iOS：Google 來源共用 G2；其他來源若有 ICS 可走 G1，保留正確來源種類。
- [ ] iCloud：驗證 Mac 日曆匯出 ICS 的最短步驟，另研究只有 iPhone 的導入方式；不要把 Mac 功能描述成 iPhone 原生匯出。[Apple Mac 匯出說明](https://support.apple.com/guide/calendar/import-or-export-calendars-icl1023/mac)。
- [ ] iCloud：比較授權連接與原生讀取的可行性；需要公開分享旅客日曆才能下載的方式，不作為預設快速導入。
- [ ] Android：驗證 Google Calendar 與常見手機內建日曆的帳號辨識，區分 Google、其他服務與僅存手機。
- [ ] Android：Google 來源共用 G2；本機來源逐款確認匯出能力，沒有匯出時再評估具讀取授權的原生匯入工具，不假設有通用匯出按鈕。
- [ ] 手機：跨裝置、同來源多 App、匯出再連線均不重複建單；檢查檔案選取、授權返回、中斷續跑與異常說明。
