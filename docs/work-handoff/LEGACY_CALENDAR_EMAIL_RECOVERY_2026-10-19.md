# Legacy calendar email recovery — 2026-10-19

The owner's latest request adds self-service email recovery for the existing two-property calendar member accounts. This supplements the earlier administrator-assisted shared temporary password flow; it does not change that flow or the separate new-customer workspace sign-in.

`/forgot-password` accepts the legacy member's login email. An active, unambiguous member with an existing personal credential receives a 30-minute link to `/recover-calendar-password`. The link contains a 256-bit random secret in a URL fragment; Redis stores only its SHA-256 digest. A new request invalidates the previous link. Suspended, unknown and `god` member records do not receive links. The initial owner credential remains outside this member recovery path.

The request endpoint uses same-origin checks, email and global rate limits, a generic response, deferred email delivery and a minimum response time. It does not reveal whether an account exists. The link is bound to the member ID, credential and current member version. Password completion requires a valid unused link and a 12–128 character password, writes with a compare-and-swap, checks the saved state, clears the token and invalidates the member's earlier sessions. A successful change sends an alert email without exposing the password. The browser removes the secret fragment from its address before making the verification request. The email links back to the current site only when its origin is the fixed primary OS host or a validated deployment under the Sweetfun Vercel team.

Local synthetic verification covers eligible and ineligible accounts, generic responses, deferred email, one-time use, expiry, replacement by a newer request, credential/member changes, old-session revocation, and the API flow. Targeted tests, TypeScript, lint and production Webpack build pass. No real member email was sent or password changed during local verification.

Release acceptance remains open: deploy a production-backed candidate, confirm the existing member can receive and use the email, then verify fresh login on the old two-property calendar. The recipient's membership cannot be confirmed without an authorized owner session. The sender must use the existing private mail configuration. The production primary aliases have not been moved for this change.
