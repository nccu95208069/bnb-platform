# Legacy calendar email recovery — 2026-10-19

The owner's latest request adds self-service email recovery for every active password-based account in the existing two-property calendar. This supplements the earlier administrator-assisted shared temporary password flow; the separate new-customer workspace already has its own email recovery.

`/forgot-password` accepts the legacy login email. An active, unambiguous member with an existing personal credential receives a 30-minute link to `/recover-calendar-password`, including an active `god` member. The separate initial owner credential, identified by the configured administrator email, uses the same entry point and an independently stored recovery record. Both link types contain a 256-bit random secret in a URL fragment; Redis stores only its SHA-256 digest. A new request invalidates the previous link. Suspended, unactivated, unknown and ambiguous member records do not receive links.

The request endpoint uses same-origin checks, email and global rate limits, a generic response, deferred email delivery and a minimum response time. It does not reveal whether an account exists or which credential store applies. A member link is bound to the member ID, credential and current member version; an owner link is bound to the current owner credential. Password completion requires a valid unused link and a 12–128 character password. Both stores use compare-and-swap; the owner transaction checks the current credential and token together before changing the password and deleting the token. A successful change verifies the saved credential, invalidates earlier sessions and sends an alert email without exposing the password. The browser removes the secret fragment from its address before making the verification request. The email links back to the current site only when its origin is the fixed primary OS host or a validated deployment under the Sweetfun Vercel team.

Local synthetic verification covers eligible and ineligible accounts, generic responses, deferred email, one-time use, expiry, replacement by a newer request, credential/member changes, old-session revocation, active `god` member recovery, initial owner recovery from both bootstrap and custom passwords, concurrent owner requests, and the API flow. No real password was changed during local verification.
