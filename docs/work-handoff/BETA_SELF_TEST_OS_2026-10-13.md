## Safe walkthrough for the account rehearsal

1. Sign in at `/start`; create **two separate synthetic workspaces/properties** if needed. Name the test records as simulations. Record each workspace slug and property ID from its own authenticated URL. Do not treat public Booking.com offer labels as physical-room IDs; for 蘭城, Villa offers may overlap the individual rooms.
2. In each property, enter the intended physical-room count and check `/w/{slug}/settings?property={propertyId}`. Enter synthetic base prices and one date override; reload and verify the saved amounts and room identities. If a Studio site proposes different room counts or prices, reject/repair the mapping before approval.
3. Choose **one** calendar branch. For a new empty calendar, confirm there are no effective unrecorded bookings or blocks in the offered period; check that `/workspaces` says the calendar is created and shows zero orders. For history import, import one **synthetic** occupied room-night and one free night. For Sheet or CSV/XLSX, use the Sheet/Excel/CSV branch of `/w/{slug}/import`; CSV/XLSX support begins only in PR #36. For ICS/ZIP, use an iOS/Android export branch. Google Calendar connection is a separate read-only path. Select the actual source/tab, map room labels to physical rooms, preview conflicts, confirm coverage, commit, reload `/w/{slug}/calendar`, and check the occupied and free nights. Repeat the same source, then revise it with a newly sold night; verify no duplicate and that the revision blocks the night. Incomplete/unresolved rows must remain unavailable.
4. Studio must prepare a new stable UUID site with the exact intended email using an opted-in server credential. Open the returned approval URL in the same browser as the email link. Compare site UUID and Studio origin, then approve the correct workspace/property and each physical-room mapping. Reload `/w/{slug}/website` and confirm `OS 尚未開放接單`. A different email/account or a second property's IDs must be rejected.
5. Share only the **information-site preview** with a friend while sales remains off. Friend can check pages, mobile layout, prices/rules as labelled preview data and that reservation checkout is unavailable. A guest reservation cannot be completed through the public site with OS sales off; do not represent this as a full booking test.
6. For the full hold → owner receipt → confirmed-email chain, use a separate protected candidate with isolated customer storage and test recipients. Verify availability and quote, create a synthetic hold, read the order and owner queue, record a clearly labelled **simulated receipt only in that isolated store**, convert the hold, then read the confirmed order and guest email provider receipt/inbox. This simulation must never be copied into the production ledger or described as real payment. Clean up test bookings and verify occupancy is zero.

## Where the complete friend flow currently stops

- **Studio → OS admission:** PR #36 has the new UUID/owner-email contract and synthetic tests, but the production OS runtime and `WEBSITE_BOOKING_STUDIO_CLIENTS.allow_new_sites` are not installed/verified. Studio must hand off the same site UUID and pending connection ID.
- **Calendar coverage:** PR #36 accepts owner-confirmed exclusive intervals for Sheet, CSV, XLSX and file-backed ICS. For a brand-new empty calendar, owner approval persists the precise website sale interval and requires a second explicit confirmation at activation; no historical file is required. The empty calendar uses OS orders/holds/blocks as authority. Imported coverage is a one-time snapshot: a new OTA/OwlNest booking after import will not synchronize itself. Connected Google cannot accept website writes. Source conflicts, shortened coverage, pending review, source connections and OwlNest fences block sales.
- **Sales-off test limit:** quote/reserve calls require `WEBSITE_BOOKING_ENABLED`, `CUSTOMER_HOLDS_ENABLED`, a ready binding and `binding.enabled`. Keeping public sales off intentionally prevents the friend from submitting a real hold. A protected isolated candidate is required for the complete chain.
- **Confirmation Email:** conversion queues `hold_converted` guest and owner notifications, but delivery is a separate cron/provider step. The original cron discovered only exact sites/bindings. This local change adds a server-owned registry written atomically at owner approval; a dedicated `WEBSITE_BOOKING_STUDIO_EMAIL_CLIENT_IDS` grant can discover only that trusted Studio client's approved UUID sites, with the site index, owner and binding checked again before sending. It requires no per-site environment edit. The grant and runtime are not deployed. Verify provider acknowledgement **and inbox receipt**; a queued status is not delivery proof.
- **Real-owner authority:** one person's simulated accounts cannot approve another owner's actual room stock, prices, listing/photos, OwlNest mapping or sender. Real sales require separate owner/provider authorization and the external room/notification checks in `BETA_PILOTS_YUYUAN_LANCHENG_2026-10-12.md`.

## Deployable isolated candidate recipe

The OS candidate must be **protected** and must use a new Redis resource with its own `CUSTOMER_WORKSPACE_NAMESPACE` and `WORKSPACE_AUTH_NAMESPACE`; a preview that inherits the production Redis connection is not isolated. Install separate candidate session/cron secrets and a test sender. Set `CUSTOMER_ISOLATED_ACCEPTANCE=true`, a distinct lower-case `CUSTOMER_ACCEPTANCE_SENDER_EMAIL` belonging to the candidate Gmail credential, and namespaces shaped like `bnb:acceptance:pilot-20261013` and `sweetfun-os:acceptance:pilot-20261013`; candidate Redis calls reject absent/default namespaces, and the mail transport refuses a missing or mismatched candidate sender. Set `CUSTOMER_DEPLOYMENT_LINKS=true` with the candidate origin; login and invitation links must never fall back to the production origin in acceptance mode. Set `CUSTOMER_ACCEPTANCE_EMAIL_RECIPIENTS` to a nonempty JSON array of exact test owner/guest inboxes plus the candidate sender used for mail setup; lifecycle/invitation/booking notices to other recipients fail before the provider call. Any account email may receive its own rate-limited login or recovery link; authentication recipients are not preselected. The candidate Studio server needs its own credential and editor origin in `WEBSITE_BOOKING_STUDIO_CLIENTS` with `allow_new_sites:true`, plus that one client ID in `WEBSITE_BOOKING_STUDIO_EMAIL_CLIENT_IDS`. Enable website booking/holds and candidate Email delivery/cron only on this isolated deployment. Keep all corresponding primary-domain settings and bindings unchanged.

Before inviting the tester, read back the candidate's Git SHA, Redis resource identity/namespace (without exposing its token), site client ID/origin, email recipient allowlist, cron status, and one new UUID binding with `salesEnabled:false`. For the controlled synthetic checkout, enable sales **only in this candidate**, use a test owner and guest address from the allowlist, and then pause it again. Read back the hold, simulated receipt, confirmed order, notification job, provider message ID and test inbox. A unique candidate URL and these readbacks are required before the link can be handed to the tester.
