# Sean Sweetfun OS、BnB SaaS OS 與 Iron Gate 的資料責任

日期：2026-10-20（Asia/Taipei）  
用途：記錄與業主討論後對齊的三個角色、目前 Google Sheet 匯入的實際落點，以及預期的訂房資料權威。本文區分**目前程式行為**、**目標架構**與**尚待定案的流程**；它不是已完成切換或正式上線的聲明。

## 一句話

**Sean Sweetfun OS 是業主自用的營運介面；BnB SaaS OS 是民宿客戶的操作介面；Iron Gate 是預計讓各入口共同使用的訂房與房況權威服務。** 使用者不需要直接操作 Iron Gate 的資料庫表。

## 三個角色，不是三張互相同步的訂房表

| 角色 | 使用者看到／操作什麼 | 目前狀態 | 目標資料責任 |
| --- | --- | --- | --- |
| Sean's Version（Sean Sweetfun OS） | Sean 每天使用的 Sweetfun 日曆與營運功能 | 正在使用；保留既有資料與整合。現在供測試的民宿客戶工作區功能仍在同一個 Sweetfun OS 網站內。 | 維持 Sean 自用環境；若日後遷移既有館別，逐館備份、核對、切換，不因 SaaS 上線而直接搬動。 |
| BnB SaaS OS 工作區 | 民宿業者登入、建立民宿／房間、提供舊資料來源、檢查匯入、看日曆及操作訂單 | 客戶工作區程式可在 Sweetfun OS 站測試；獨立的 SaaS 正式站與測試站專案已建立，但截至本文日期尚未部署上線。現在確認匯入的訂單仍保存在 OS 工作區資料儲存。 | 保存帳號、會員權限、民宿設定和操作狀態；訂單與房況透過 Iron Gate API 讀寫，不在 OS 維護第二份訂房正本。正式站和測試站的帳號／設定資料須隔離。 |
| Iron Gate Service | 主要由 OS、網站、LINE 等服務呼叫的私有 API；不是業者另開的日曆網站 | 有獨立 PostgreSQL 與受保護的測試部署；正式入口固定回 503，沒有任何真實館別或訂單完成遷移與接單切換。 | 唯一權威的訂單、房晚占用、保留與相關事件資料；跨入口的新增／修改先檢查房況，再寫入與讀回。 |

這裡的「三個角色」不等於替每個客戶建立一張實體 SQL 表，也不等於三個地方各存一份可獨立修改的正式訂單。民宿名稱及可辨識的專案代碼是對外識別；內部以工作區、館別、房間與訂單 ID 做隔離。BnB SaaS 正式站／測試站是兩個部署環境，**不是**兩份應互相同步的正式訂房資料。

截至本文日期，規劃中的 BnB SaaS 正式／測試站已各有 Vercel 專案，並在**同一個新的 Supabase 專案內以不同 schema 與登入角色**準備隔離的工作區資料；兩站尚未部署或接入使用者。Iron Gate 則有**另一個**專用 Supabase 專案。這些部署／資料庫數量，與上表的三個產品角色不要混為一談。

## 現在：業主正在測試的 Sheet 匯入實際流向

業主已用**真實訂單 Google Sheet 的副本**，把副本網址貼進 OS 客戶工作區，測試欄位辨識、轉換預覽和日曆。這是實際的匯入流程測試，不應描述成「沒有做匯入」。

```text
Google Sheet 副本（唯讀來源）
  → OS 讀取、辨識欄位、顯示預覽
  → 使用者按「確認匯入」
  → OS 工作區資料儲存中的 workspace.bookings
  → OS 工作區日曆
```

- **只貼網址／看預覽**：尚未保存轉換後的訂單。
- **按確認匯入**：目前的 [`commitImport`](../../frontend/src/lib/customer-workspaces/sheet-import.ts) 將可匯入的訂單提交至 OS 的 `CustomerStore`，加入該工作區的 `bookings`；有疑問的來源列留下 `reviewRecords`。匯入前重新核對來源與房間衝突。此路徑不呼叫 Iron Gate。
- **看 OS 工作區日曆**：目前的 [客戶日曆頁](../../frontend/src/app/w/%5Bslug%5D/calendar/page.tsx) 讀取 OS 的 `Workspace` 並投影給日曆；它不是每次重讀 Google Sheet，也不是從 Iron Gate 讀取。來源 Sheet 副本在這條匯入路徑不被改寫。
- 這裡說的「OS 自己的資料」是**工作區資料儲存**，不是另一張 OS Google Sheet。現有 Sweetfun 站的客戶工作區和 Sean 自用功能同處一個部署，但客戶工作區使用獨立命名空間；Iron Gate 使用另一個專用資料庫。

因此，業主正在測試的轉換與日曆畫面值得延續；缺口在**確認匯入後的資料權威位置，以及後續訂單寫入路徑**，不在要求業主重做一套 UI 測試。

## 目標：Iron Gate 成為訂房唯一正本

```text
新民宿：BnB SaaS OS 建立工作區／館別／房間
已有紀錄：Sheet／Excel／行事曆等來源 → OS 辨識與人工核對
兩者的正式訂房操作 → Iron Gate API → Iron Gate 權威訂單與房況
BnB SaaS OS 日曆 ← Iron Gate API 的授權讀取結果
```

對**全新民宿**，OS 協助建立民宿名稱、專案代碼、房間及權限，Iron Gate 建立隔離的館別資料空間，從零開始記錄訂單；不預設一館一張實體資料庫表。對**有既有紀錄的民宿**，沿用 OS 的來源讀取與轉換預覽，補上寫入 Iron Gate 前的欄位語意、房晚、付款和衝突核對，再由一條受控匯入路徑保存。其他入口（網站、LINE、財務及必要的外部通路）應透過 Iron Gate 的權限與事件契約對接，避免 OS 和 Iron Gate 同時成為 writer。

### 討論中的匯入體驗原則（尚未定案／尚未全部實作）

先以唯讀方式解析來源，批次詢問「欄位代表什麼」「來源房名對應哪間房」「哪些列屬同一訂單」「取消或有效的判斷規則」，再集中處理例外；不得僅憑相同客人姓名合併訂單。缺客人姓名、價格或付款資訊，可以標為未知供後續補齊；缺可確認的日期、房間或有效狀態時，不得猜測為已確認占房。來源列與人工決定要保留可追溯性。

討論中區分兩道門檻：**看匯入預覽／可確認部分的日曆**，和**開放目前及未來房晚接新單**。後者必須先排除可能撞房的未決資料、確認來源涵蓋及權威、備份和回復方案。這是討論中的產品原則，具體畫面與逐來源規則仍需設計和驗收，不能把它當作已上線保證。

## 切換前仍須完成

1. 把 OS 現有「確認匯入」與日曆讀取接到 Iron Gate，同時保留目前已測的欄位辨識及人工確認體驗；逐筆核對 OS／來源與 Iron Gate 的訂單、房晚、狀態與必要財務欄位。
2. 盤點並改接原生訂單、保留、付款、取消／改期、網站和 LINE 等寫入入口；逐館關閉舊 writer，不能雙寫兩份正本。需要 OwlNest 的館別，另核對其房量寫入與回讀。
3. 對真實館別執行備份、影子比對、衝突處理、受控切換及可演練的回滾；確認權限、監控與端到端結果。未完成前，Iron Gate 正式入口維持關閉。
