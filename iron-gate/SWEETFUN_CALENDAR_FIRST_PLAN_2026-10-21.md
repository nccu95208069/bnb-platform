# 水芳日曆先行遷移與 Gmail 接線計畫

日期：2026-10-21（台北時間）

這份計畫記錄業主在本次討論決定的執行順序。**先證明水芳 OS 工作台日曆能完整理解並顯示 Iron Gate 的訂單格式，再轉換舊表、逐筆核對；接著補 Gmail check order 寫入 Iron Gate；LINE 與 OwlNest 最後處理。** 第一階段的成果是可檢查的唯讀日曆，不代表 Iron Gate 已接管正式接單或對外房量。

## 已有的成果與真正缺口

| 項目 | 目前狀態 | 對本計畫的用處 |
| --- | --- | --- |
| 舊表轉換 | 已有轉換程式；專用 Iron Gate 資料庫中的水芳影子為第 8 版，1,605 張訂單（其中 1 張已取消）、1,755 個占房房晚，`readOnly=true`、權威代次 0。 | 保留作後續真實資料核對樣本，不重做已完成的轉換。這份固定快照不是持續更新的正式日曆。 |
| Iron Gate 訂單讀取 | 已有訂單清單及逐房晚房況讀取 API。 | 可提供 OS 日曆所需的訂單與占房資訊。 |
| 水芳 OS 日曆接頭 | `/api/v1/bookings/calendar` 已有預設關閉的 Iron Gate 讀取候選和合成測試，但目前要求 Iron Gate `readOnly=false`、權威代次至少 1。 | 現有唯讀影子會被接頭拒絕；必須先增設明確的「固定快照預覽」讀取模式，並保持正式接單功能關閉。 |
| 工作台畫面 | 水芳 OS 日曆仍讀原有日曆來源；客戶工作區 `/w/[slug]/calendar` 另讀 OS 工作區資料。兩種畫面不是同一條讀取路徑。 | 本計畫第一個畫面目標是水芳自用工作台 `/calendar`。客戶工作區之後另做相同契約接線，不把兩條路徑混稱為已完成。 |
| Gmail、LINE、OwlNest | Gmail 新處理程式為 0% 流量、功能關閉的候選；LINE 及 OwlNest 沒有改接 Iron Gate。 | 不阻擋先驗證唯讀日曆。 |

## 第一步：先讓日曆吃懂 Iron Gate 格式

先用**合成訂單**走完「Iron Gate API → OS 日曆 API → 工作台日曆畫面」，不匯入新的舊表資料，也不改正式來源。逐欄核對日曆要顯示的內容：

| 日曆需要的內容 | Iron Gate 現況 | 本步要確認或補齊 |
| --- | --- | --- |
| 館別、房間 | 訂單有館別與房間 UUID；OS 接頭已有六間水芳房號對照。 | 對照固定且無重複；畫面逐房顯示正確。 |
| 入住、退房與占房房晚 | 訂單有 `stays`，房況 API 有逐晚 `sold`／`blocked`／`unsold`。 | 跨日、連住、多房訂單及退房當天顯示一致；訂單與占房房晚雙向核對。 |
| 訂單身分與客人 | Iron Gate 有訂單 UUID，授權後可讀客人姓名；現有接頭以 `IG-UUID` 當畫面訂單識別。 | 同一訂單不因分頁或跨房晚變成不同訂單；有疑問的姓名標示待核，不猜測。 |
| 平台、原訂單號、訂房日期 | 轉換後的影子保存來源證據，但目前的日曆公開投影把平台顯示為「其他」、訂房日期為空，也沒有把原訂單號送到畫面。 | 制定受權讀取的欄位對照；能可靠對應才顯示原值，否則清楚標示未知，不用虛構值。 |
| 房價、付款、備註 | 現有日曆候選把房價隱藏、付款標為未知、備註為空；舊表財務尚未成為 Iron Gate 付款事件。 | 首批訂單／房況驗證維持「財務未遷入」的明確標示；不得把舊表付款欄推論為已對帳收款。必要備註另按權限與來源語意決定顯示方式。 |
| 唯讀與資料時間 | 固定快照預覽接頭已完成合成資料驗證；真實影子現為第 8 版，仍無 OS 讀取憑證。 | 使用**獨立、預設關閉**的固定快照預覽模式，只接受預期版本、`readOnly=true`、代次 0；畫面明示「固定快照／不接單」與快照時間。 |

若任何日曆必需欄位缺失，先補讀取契約與畫面對照，再做舊表最終轉換。這一步只驗證一條完整的顯示流程和少量有代表性的合成情況；不進行真實 OwlNest 關房、觸發器操作或反覆重跑整套接單測試。

**完成標準：**已登入且有水芳權限的使用者，能在工作台日曆看到合成訂單的正確房間、日期、訂單歸屬和資料狀態；無權使用者看不到。訂單清單與逐晚房況一致；讀取失敗時畫面報錯，不退回另一份可能過時的訂單。業主能直接看到這個畫面，並確認哪些欄位完整、哪些仍標為未知。

## 第二步：一次轉換舊表並逐筆核對

第一步通過後，沿用已完成的轉換程式，以一份固定的舊表私人副本建立或更新 Iron Gate 唯讀資料。第 8 版可先拿來驗證整條日曆讀取路徑；**此時不為了維持「隨時最新」而反覆追單**。舊 Sheet 與既有 Gmail 接單照常運作；畫面清楚標示快照時間，不能把固定快照說成即時房況。

核對以程式對**每一列來源 J、每一張轉換後訂單、每一個房間日期**做全量比對：來源列應各有唯一去向（接受、隔離待核或已確認取消）；訂單 ID、房間、入住／退房、逐晚占用不能遺漏、重複或撞房。再讓 AI 在受限環境中**分批逐筆檢視全部來源與轉換結果**，特別標出程式發現的差異和無法自動判定的欄位；AI 不憑姓名或推測自行合併、刪除訂單，也不以口頭「看起來對」取代逐筆對照。留下去個資的吻合數、差異數和人工決定，讓業主檢查結果。需要對照畫面時，用同一版來源副本與 Iron Gate 版本，不拿不同時間的兩份資料互相比。

**完成標準：**OS 日曆顯示該固定版本的真實訂單；來源列、訂單、逐房晚的總數與雙向對照吻合。所有例外有明確「待核」狀態，不被當成空房。業主可直接看日曆及差異摘要。開發與核對結束後，才從仍持續收單的舊表**一次補齊期間差額**，再做一次同樣的全量核對；在此之前不宣稱新日曆是最新正式房況。

## 第三步：補 Gmail check order → Iron Gate

日曆和舊資料核對完成後，才處理新訂單的持續流入。Gmail check order 的新增、修改、取消都要有同一來源訂單身分與事件鍵；寫入 Iron Gate 後以該鍵查回訂單和房晚，結果不明時不盲目重送。先讓舊 Sheet 保持正式接單來源，對照 Gmail 事件與 Iron Gate 結果；確認穩定後，另訂停寫、排空、最後差額和單一正式 writer 的切換窗口。不能因為 Gmail 候選已部署為 0% 流量，就說它已經更新 Iron Gate。

**完成標準：**在受控情況下，新單、改單、取消各有一次寫入與讀回證據；同一事件重送不產生第二張訂單；OS 日曆能顯示更新結果。正式導流仍是另一個明確決定，先前的唯讀日曆驗收不等待它。

## 第四步：LINE、OwlNest 與其他入口

Gmail 線路穩定後，再逐一處理 LINE 小助手、人工新增／修改、網站及 OwlNest 房量。每條入口要共用 Iron Gate 的訂單身分與房晚規則，但各自驗證授權、結果讀回和異常恢復。這些工作**不列入前兩步的完成條件**；現在不需要業主提供 OwlNest 測試房晚或 Apps Script 觸發器帳號。正式接單權威與對外房量切換時，再按當時的實際狀態處理舊 writer、觸發器和回退。

## 執行約束與回報方式

1. 依上述順序交付可見成果：先合成日曆畫面，再真實固定快照的日曆及逐筆差異，接著 Gmail 持續更新。每完成一步，給業主畫面或可直接檢查的結果、資料版本、吻合／待核數，而不只報告測試數量。
2. 只做能驗證當前步驟的測試：第一步驗證欄位與畫面；第二步做來源到目標的全量對照；第三步驗證 Gmail 三種訂單事件及重送。其他通路與正式切換測試留到相應階段。
3. 原 Sheet、舊 Gmail／LINE／OS 正式流程維持運作；Iron Gate 第 8 版維持唯讀，Production 入口仍不接單。任何需要變更正式 writer 的步驟，先準備可檢查的切換與回復結果，再請業主決定。
