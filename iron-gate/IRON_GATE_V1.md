# Iron Gate：訂房資料核心服務 v1

狀態：產品契約與遷移準則；**合成 API 核心已實作，尚未上線或接真實資料**
日期：2026-10-13（Asia/Taipei）

## 1. 產品定位與已確認決策

Iron Gate 是供內部服務呼叫的訂房資料入口。新客戶沒有外部訂房／通路平台時，它是訂單與實體房晚占用的唯一正本；有 OwlNest 時，它維護內部訂單與房晚狀態，協調通路同步、保存每次外部讀回證據，不能把兩邊尚未核對的狀態當作可售。

業主在本聊天確認：

1. Sweetfun／OFFLAND 逐館核對並遷移後才切換正本；每次遷移前先完成備份與可操作的回滾準備。
2. Iron Gate 與 OwlNest 的訂單或房態矛盾時，該房晚停止接單並進入人工核對。
3. 對外所說的「刪除訂房」是**取消訂單**；原紀錄、付款與稽核軌跡保留。
4. 第一版交付**獨立內部服務**，OS 也透過 Iron Gate 讀寫訂房資料。

第 4 項是業主在本聊天確認的服務邊界；不要求在第一天把既有兩館的正本從 Sheet 強行搬走。

服務拆分的原則是**一個訂房寫入入口、一份權威資料**。切換後，OS、LINE OA、官網、財務、分析、清掃及定價服務不得繞過 Iron Gate 直接改訂單儲存。Iron Gate 初期可以透過受控儲存介面承接現有 OS 原生訂單資料；不能先複製出另一份可獨立修改的「Iron Gate 訂單庫」。

每館有持久的寫入權威狀態與遞增切換代次（`authorityEpoch`）。所有可改變訂單、保留、房晚、封房或收退款的舊路徑，在該館切換前必須逐一改為轉送 Iron Gate，或在舊儲存層拒絕寫入；不能只修改 OS 畫面的呼叫。未切換的館仍由其原權威系統寫入，Iron Gate 不得另建可寫副本。切換時排空進行中的請求，舊代次請求即使延遲抵達也須被拒絕；切換後以實際讀回證明沒有旁路寫入。

## 4. Canonical Booking v1（目標 API 語意）

以下是 Iron Gate 的**目標 JSON 契約**，不是宣稱現有 OS 欄位已全部相同。實作時須對齊既有 `Booking`、標準帳本 v4，並提供版本化轉換，不得直接更改歷史資料語意。

| 欄位群 | 必要語意 |
| --- | --- |
| 身分與版本 | `workspaceId`、`propertyId`、`bookingId` 為 UUID；`bookingVersion` 每次接受訂單異動遞增；`inventoryVersion`／工作區版本用於房晚寫入競爭檢查。儲存層的每次寫入另須核對伺服器掌握的該館 `authorityEpoch`，不採信呼叫者自報代次；舊代次不得寫入。 |
| 住宿 | `stays[]` 每段有 `checkIn`、`checkOut`、實體 `roomIds[]`；入住日包含、退房日不包含；同一訂單可多房、多段且中間空檔不占房。 |
| 狀態 | 訂單生命週期 `held`、`confirmed`、`cancelled`；保留到期仍占房，只有核實轉正式或釋出才改變占用；取消不物理刪除。另有獨立的 `channelSyncState = not_required / pending / verified / review_required` 與對外操作狀態，不把通路同步結果塞進訂單 `status`。內部 `confirmed` 僅代表本地訂單已寫入；有外部通路時，對呼叫者與旅客不得僅憑它宣稱通路關房或完整確認。 |
| 客人 | 姓名、聯絡方式、備註分欄；未知使用 `null`，不能以空白或推測值冒充。非必要消費者不收到這些欄位。 |
| 金額 | `totalCents`、來源累計已付、已核實實收、退款、尾款分開；幣別明示。未知為 `null`，已知零為 `0`。來源累計已付不等於旅宿銀行實收；來源沒有逐晚房價時不平均捏造。 |
| 來源與追溯 | `sourceSystem + sourceAccount + propertyId + externalOrderId` 唯一識別外部紀錄；來源連結同時保存 `sourceVersion` 與上次成功套用的 `lastAppliedBookingVersion`。另保留來源列／活動 ID、觀測時間、匯入批次、指紋及原始訂房日期。不能用客人同名、相鄰房晚或建檔時間猜測。 |
| 稽核 | 每次指令的操作者／服務、請求 ID、預期與結果版本、前後狀態摘要、外部讀回、時間及結果；敏感原文不進一般日誌。 |

實體房間 ID 是撞房的唯一單位。房型、包棟方案與網站內容 ID 需要屋主核准的 mapping；同一包棟方案涵蓋的房間不能再被單房方案獨立出售。`bookedAt` 是來源訂房日期，`createdAt` 是系統建立時間，兩者不能互代。訂單主額只記一次，住宿明細的多房多晚不得重複加總。

API 操作回覆與訂單生命週期分開：無外部通路時 `channelSyncState=not_required`；有通路且本地交易已讀回時回 `sync_pending`，逐晚外部驗證後回 `sync_verified`，失敗或不確定時回 `review_required`。查詢原操作鍵須回目前狀態與原訂單 ID／版本，不因重試建立第二張訂單。`sync_pending` 和 `review_required` 都不得向旅客呈現為通路已完成確認。

## 5. 服務 API 草案

**以下路徑仍未部署；已實作與仍僅規劃的範圍以 [API v1 現況](API_V1.md) 為準。** 所有寫入以 `Idempotency-Key`、預期版本與伺服器端館別權限為基本條件；同鍵同內容重試回原結果，同鍵不同內容回 `409`。逾時只查原鍵，不換新鍵重做。

| 動作 | 提議路徑 | 主要使用者與限制 |
| --- | --- | --- |
| 查詢訂單／搜尋 | `GET /v1/properties/{propertyId}/bookings/{bookingId}`、`GET /v1/properties/{propertyId}/bookings` | 依服務與館別回最小欄位；查不到、無權限及來源不可用分開回應。 |
| 查詢房晚與可售判定 | `GET /v1/properties/{propertyId}/availability` | 回 `sold / held / blocked / unsold / unknown`、來源時間與停止原因；`unsold` 只表示內部無單，不保證通路可賣。 |
| 新增訂單 | `POST /v1/properties/{propertyId}/bookings` | 受權限服務提供請求 ID、預期房晚版本與已核對來源；原子撞房檢查、寫入、讀回。有通路連線時，訂單與待同步操作／房晚 fence 須一起持久寫入，回覆需明示 `sync_pending`、`sync_verified` 或 `review_required`；網站仍須先走短效報價與開賣檢查。 |
| 修改訂單 | `PATCH /v1/properties/{propertyId}/bookings/{bookingId}` | 僅白名單欄位；body 須帶預期訂單及房晚版本；本地改期／改房重新檢查所有受影響房晚。OwlNest 改房仍拒絕。 |
| 取消訂單 | `POST /v1/properties/{propertyId}/bookings/{bookingId}/cancel` | 保留歷史、來源與收退款；目前原生訂單若有未沖銷收款會先拒絕取消，須處理財務結算；來源訂單須來源協調。`DELETE` 不提供一般訂房操作。 |
| 登記收退款事實 | `POST /v1/properties/{propertyId}/bookings/{bookingId}/payment-events` | 僅有財務寫入權限者，需來源憑據、事件 ID、版本；更正採沖銷／新事件，不改舊事件。 |
| 查詢請求結果 | `GET /v1/properties/{propertyId}/requests/{requestKey}` | 解決回應遺失；請求鍵的收據綁定原服務／grant、館別、動作與請求摘要，查詢時重新授權，只回原操作與權威讀回版本，不重建訂單或洩漏跨館結果。 |
| 外部來源同步 | `POST /v1/source-events`、`GET /v1/source-events/{eventId}` | 僅來源專用 grant；必須提供來源帳號、外部訂單 ID、真正來源版本、`previousSourceVersion` 與預期房晚版本。來源連結的 `lastAppliedBookingVersion` 不等於目前訂單版本時，拒絕覆寫／取消並進入待核對；舊事件、亂序取消及房晚衝突亦同。 |
| 通路房晚保護 | `POST /v1/inventory-operations`、`GET /v1/inventory-operations/{operationKey}` | 在 OwlNest 操作前設不可自動失效的房晚 fence；逐晚外部讀回且內部再核對後才釋放或定案。 |
| 事件訂閱／投影 | `GET /v1/properties/{propertyId}/events?after=…` | 依消費者權限提供去個資版本事件與持久 outbox 游標；正式傳送、重試與故障恢復仍待接線。 |

安全錯誤需固定代碼，例如 `UNAUTHORIZED`、`FORBIDDEN`、`VERSION_CONFLICT`、`ROOM_CONFLICT`、`SOURCE_CONFLICT`、`SOURCE_UNAVAILABLE`、`WRITE_UNCONFIRMED`；不得在錯誤中帶客資、原始郵件、上游 HTML 或憑證。

每個服務使用獨立機器身分及可撤銷的 `workspace/property/action/field` 範圍，不能共用全域金鑰。服務間請求只由伺服器發送，以 TLS、受眾綁定、短效或可輪替憑證、速率限制及 `private, no-store` 回應保護。每次查詢與寫入重新核對館別、操作者及適用的 grant／旅客訂單憑據狀態。瀏覽器、LINE 訊息、網頁前端與日誌不能取得服務祕鑰、OwlNest 帳密或整份未過濾的訂單。原始 PII 必須依用途限制、加密保存、可稽核存取；跨館讀寫以伺服器端拒絕。

## 7. OwlNest 與其他來源同步

### OTA 訂單進來

來源 connector 先驗證 provider、帳號、外部單號與來源版本，再查同一來源連結。Iron Gate 只接受已核實的來源事件；同事件重送不增單，取消早於成立時留 tombstone，舊成立事件不能重新復活。每次 upsert／取消須在同一房晚版本檢查中同時比對 `previousSourceVersion` 及 `lastAppliedBookingVersion`：若訂單自上次來源事件後已被 OS、LINE 或人工修改，來源連結標 `diverged`，拒絕覆寫／取消，進人工核對並停止受影響房晚接單；來源版本吻合也不能略過此檢查。房晚與既有訂單／封房衝突、版本倒退、來源消失但無明確取消，亦建立待核對紀錄並停售。Email 到達時間不能充當來源訂單版本。

### 直訂或 LINE 訂單要影響 OwlNest 庫存

對直訂或 LINE 建單，Iron Gate 以同一操作鍵和房晚版本，在一次權威儲存交易中完成撞房檢查、持久訂單、待同步操作及關聯房晚 fence；該 fence 保護其他請求，但同一訂單的完成檢查不得把自己的 fence 誤判為撞房。儲存讀回成功表示**本地接單已成立、通路同步仍待完成**，回覆 `sync_pending` 並附訂單 ID、版本和操作鍵；不可回覆「OwlNest 已關房」，也不可觸發旅客的完整確認通知。若本地交易未能讀回，以同一操作鍵查結果，不重新建單。

OwlNest connector 以該館專用憑證與屋主核准 mapping 逐晚讀取、執行關房，再逐晚讀回。Iron Gate 用同一操作鍵核對所有房晚的來源版本、讀回與最新內部占用後，原子地將 `channelSyncState` 設為 `verified` 並解除多餘 fence；訂單本身持續占房。只有這個狀態可以向呼叫者宣稱通路同步完成，後續通知仍須獨立確認送達。部分失敗、逾時或外部結果未知時，訂單及 fence 保持、`channelSyncState` 轉為 `review_required`、該房晚停售並建立修復工作；重試沿用原操作鍵，不重新建單。取消可保留本地取消紀錄，但要另設持久 fence，直到外部開房逐晚讀回且再次確認沒有其他占用後才釋放可售；有款待退另外核對，不能把取消等同退款或通路已開放。

改期或改房須同時保護變更前後的房晚，核對新房晚關房及舊房晚開房的各自讀回；任何一側不確定時保留相關 fence 與待核對狀態。不能因新訂單日期已寫入，就立即把舊房晚當作可售。

**官網與來源連線共同開賣閘門**：現行 OS `customer-sources/v1` 的首個 setup-code exchange 會停用該館網站 binding，來源連線存在時也不能重新啟用。Iron Gate v1 在替代能力完成前沿用停售狀態，不能以新 API 繞過它。要讓同一館同時使用官網訂房及 OwlNest，須先讓網站 binding 與來源 grant 指向同一 Iron Gate 館別與房晚寫入閘門，完成屋主核准的房型映射、來源帳號、逐晚真實讀回、最後一間競爭、未知結果停售、撤銷與跨館隔離測試；之後才以館別開關取代既有互斥規則並由屋主明確開賣。該館開賣所依賴的 grant 待驗／撤銷、映射或來源涵蓋不足、房晚待核對、讀回過期或 fence 未解，都關閉該房晚的官網銷售。

OwlNest 憑證留在 connector 的祕密管理處；Iron Gate 只保存授權 grant、房間映射、操作狀態、版本及最小讀回證據。舊館 `sweetfun/offland` 的 ID 與新客戶 UUID 不混用；既有 `/api/v1/calendar/changes` 不是新租戶訂單 API。

## 8. 逐館遷移、備份與回滾

遷移不是一次全站切換。每一館單獨有 `legacy_authoritative → shadow_verified → cutover_ready → iron_gate_authoritative` 狀態，狀態及版本持久保存；未過門檻不得跳級。備份與回滾演練是 `cutover_ready` 的必要條件。

1. **盤點與備份**：記錄該館主 Sheet 的分頁／表頭／欄位語意、來源 ID、完整訂單與付款、封房、OwlNest 房型映射及觀測時間；建立有時間戳、存取限制和完整性雜湊的 Sheet 副本、OS 私有儲存／付款與回執快照、來源對照表。備份必須能在隔離環境實際還原並核對筆數與房晚，不以「有檔案」代替演練。
2. **唯讀影子轉換**：按既有標準帳本規則轉成一張訂單與多筆房晚；保留舊 ID／列號／來源版本、未知金額及衝突。逐房逐日比較訂單、封房、有效房晚、已收款與來源別名；缺 ID、不明分組與 OFFLAND O／Q 欄位差異先核對，不用姓名猜合併。
3. **切換前驗證**：用兩個合成租戶先驗跨館拒絕、最後一間競爭、重送、取消、付款與來源中斷；再在該館真實資料上只讀核對。逐一盤點並驗證所有可能寫入的入口：OS 原生訂單／保留／付款／封房、網站預約與改單、LINE `owner-actions`、`customer-sources/v1/bookings` 與 inventory guard、Sheet／日曆匯入，以及該館舊 Sheet／OwlNest 作業；停用的候選端點也要證明啟用後不會繞寫。舊館 `/api/v1/calendar/changes` 僅是權威寫入後的通知入口，不是訂單 writer；須盤點並封住或轉接它上游的 Sheet 訂單寫入者，不能以停掉通知冒充封寫。確定舊 writer 可暫停、排空在途請求並拒絕舊切換代次，能捕捉切換期間的增量，並完成最新 OwlNest／Sheet 讀回。
4. **原子切換入口**：在權威路由紀錄上遞增該館 `authorityEpoch`、封住所有舊寫入入口並排空在途請求，套用最後增量，比對版本與房晚，再將所有該館寫入導向 Iron Gate；任何攜舊代次的延遲請求由儲存層拒絕。若無法讓每一條入口同時受此閘門保護，不得把該館標為已切換。**不能長期雙寫兩份正本**。切換時保留原始備份、ID mapping、最後舊版水位與新服務操作 journal。
5. **切換後觀察**：讀回同一訂單、房晚、付款、取消與外部庫存；觀察來源延遲、失敗、資料差異和可售閘門。未完成外部讀回的館別仍維持停售。

**回滾程序**須在切換前演練並指定操作者。切換前失敗：保留舊正本，丟棄候選投影即可。切換後若程式故障：優先回退 Iron Gate 程式版本並沿用同一權威資料；若資料錯誤，先停止該館寫入及銷售、保存事件 journal，從經驗證備份恢復並重放切換後已接受的操作，逐筆核對再開放。不能直接把舊 Sheet 復原覆蓋切換後的新訂單或付款。無法證明資料一致時維持停止接單，交人工修復。每次回滾須有演練結果、時間點、快照 hash、重放清單、差異報告與業主可讀的狀態。

## 9. 第一版交付順序與驗收

1. 凍結 Booking v1 的 JSON Schema／OpenAPI、欄位權威矩陣、狀態機及服務權限矩陣；為現有 OS、網站和 LINE 契約建立相容測試。上述路徑在此之前僅是草案。
2. 實作獨立 Iron Gate 服務與私有儲存 adapter；先承接一個**沒有 OwlNest 的合成租戶**。依第 8 節盤點的所有寫入入口逐條導流或封寫，再以館別權威路由及 `authorityEpoch` 切換；讀回同 ID／版本／房晚，確認舊端點無法旁路寫入。
3. 驗證另一個合成租戶與跨館拒絕、平行最後一間、重送／回應遺失、改期、取消、已收款取消、權限撤銷、匿名拒絕、PII 紅線、故障恢復；另驗 LINE grant 預設只能列出及操作自己建立的訂單，來源訂單被人工改過後的來源 upsert／取消須拒絕覆寫。
4. 接上來源 grant、外部事件、OwlNest fence 與逐晚讀回；驗證本地接單成功但通路關房失敗、逾時及部分成功時的 `sync_pending → review_required／sync_verified`、同鍵查詢與停售。provider 實測前保持預設關閉與停售。官網與來源連線要並用時，先通過第 7 節共同開賣閘門，才能取代舊網站 binding 的互斥規則。清掃、分析、定價先接最小唯讀投影，財務付款寫入另做來源核實與稽核。
5. 依第 8 節逐館完成 Sweetfun／OFFLAND 備份、還原演練、影子比對與切換；兩館可分不同日期，不以一館通過推論另一館通過。

完成的證據應包括：正式授權身份下的成功與拒絕讀回、兩個租戶互相不可見、每條舊寫入入口的導流／拒絕及舊代次拒絕、同一房晚最後一間只能一筆確認、取消保留歷史、已收款不自動退款、LINE 預設範圍與來源 `diverged` 拒寫、OwlNest／Iron Gate 逐晚一致或明確停售、網站與來源並用時的共同開賣閘門、備份可還原、切換後可按 journal 回滾。合成測試通過不等於真實業主和 provider 驗收；真實接單開關須另以該館證據決定。

## 10. 尚待工程查證，不能自行假定

- 既有 OS 原生訂單儲存的備份／還原能力、容量與一致性界線；獨立服務的正式部署與私有網路方案。
- Sweetfun／OFFLAND 實際欄位與來源版本，尤其 OFFLAND O／Q 訂單 ID 差異；每館真實房型／包棟映射及 OwlNest 可驗證的逐晚讀回。
- 外部 OTA 郵件能否給出可排序的真實訂單版本；沒有版本時需保持人工核對，不用收信時間替代。
- 各消費服務的實際身分、必要欄位與發送端；以合成契約測試通過後再配置各自 grant。
- 個資保存期限、刪除個資請求與法務需求需另訂；不得把日常「取消訂房」當成個資銷毀。

本文件是 Iron Gate 的起點。任何未經上述驗證的候選 endpoint、同步或遷移，都不得在產品中顯示為已可用。

API 的已實作範圍、合成驗證與後續接線見 [API v1 現況](API_V1.md) 與 [OpenAPI 草案](openapi.yaml)。目前有記憶體、SQLite 與 PostgreSQL adapter；只用合成資料驗證，未接正式 OS、OwlNest 或遷移舊館。
