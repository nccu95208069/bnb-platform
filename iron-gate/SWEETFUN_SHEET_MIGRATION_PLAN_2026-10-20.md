## 不可破壞的原則

1. **遷移作業不改原表。** 準備、快照、轉換、試轉、核對只做 Google Sheet 唯讀取得；不改儲存格、格式、公式、權限、工作表或分享設定。切換前原本獲授權的 Gmail／營運寫入照常運作；遷移工具不得取得 Sheet 寫入憑證。
2. **一個館別同一時段只認一個正式權威。** Gmail、OS、LINE 可以是不同操作入口，切換前仍須服從各自已核實的舊正本；Iron Gate 影子狀態不可對外接單。切換時把全部舊寫入入口封住或改接，驗證後才放行 Iron Gate。不得讓舊表與 Iron Gate 各自接真單再嘗試合併。
3. **可重跑、可追溯、失敗關閉。** 來源 J 唯一 ID、L 訂單編號、N OTA 訂單編號各保留不同意義；來源列號只是位置。每個轉換決策、原始版本、人工修正及目標 UUID 需有私密、版本化對照紀錄。相同來源版本重跑不得再生訂單；不同內容不得靜默覆蓋。
4. **不猜未知。** 不能依客人姓名、相鄰列或金額猜測同一訂單；缺房、日期、有效狀態、來源覆蓋或重疊房晚需隔離並擋住該房晚開賣。H 的 `done`、卡欄位或 OTA 欄位不等於已入帳，刪除的列不自動等於取消。
5. **保留回復能力。** 切換前做來源、OS 資料與 Iron Gate 的加密備份及實際還原演練；切換後原 Sheet 保留唯讀封存與稽核，不刪除。若必須回退，先停止 Iron Gate 新寫入、核對切換後新增／變更，再將這些差額受控回填到舊權威，不能直接把舊版 Sheet 重新打開接單。

### 訂單相關財務：獨立盤點、逐事件核對

主表 G 是房費，H 是支付標記，H 註記可能含收款線索；活頁簿還有 `退刷單`、`財務異動紀錄`、`訂單收款摘要` 等分頁。Sweetfun OS 另有私有收款帳本與逐年財務帳本。較新 LINE 程式與 2026-10-20 歷史發布紀錄顯示，LINE 財務確認先保存 Firestore `line_finance_v1_books` 分筆帳本、版本、操作回執、audit 和 outbox，再把異動及訂單摘要投影到兩個受保護的 Sheet 專頁；不寫主表付款欄。這些歷史證據仍須以目前 Cloud Run revision、Firestore 原始紀錄及 Sheet 投影回執獨立驗證。資料需要按「訂單金額／約定訂金／期初／實收訂金及尾款／其他費用／退款或退刷／OTA 代收與旅宿入帳／營運收支」分開列來源、事件 ID、日期、付款方式與帳戶。不能把 H 的 `done` 變成一筆虛構收入，也不能把同一次收款從 H 註記、LINE Firestore 與 OS 帳本各匯入一次；LINE 的作廢版本也不能冒充退款。

Iron Gate 預計保有**訂單關聯的已核實收退款事件**，但它目前的財務欄位不能完整承接 OS 的配置、期初、來源金額等語意。完整遷移前要補足契約與回讀，或保留受權財務領域的原始帳本並與 Iron Gate 訂單 ID 對上；非訂單的費用、銀行對帳與報稅不應假裝已搬進 Iron Gate。所有原有財務帳本均須備份與核對，不能因訂單切換而遺失。

業主於 2026-10-21 表示目前沒有可提供的外部銀行／刷卡交易憑據。遷移因此以**忠實保存原帳本主張與原始回執、逐筆對上來源訂單、明示外部結算未驗證**為可執行的資料目標；這不等於認定款項未收或已收。不能因缺憑據捏造已對帳現金，也不應抹除既有帳本。正式切換前仍須確認受限財務領域可讀回每筆原始主張、版本與未對帳標記，報表和 API 不把它們升格為銀行／刷卡已入帳金額；未來取得獨立憑據時再追加逐筆對帳結果，不改寫原快照。

## Gmail check order 是遷移主線，不是後續附加同步

**切換前流向：**平台郵件 → Gmail Watch／Pub/Sub 或補收 → 訂房小助手解析與訂單辨識 → Sweetfun Sheet 寫入與讀回 → Sean OS 監測。這條路徑繼續使用。業主建議增加一段**受控平行寫入**：同一封郵件的持久事件，在舊表寫入並讀回成功後，也送到與正式服務隔離的 Iron Gate 影子館別，持續比對結果。影子可以接收遷移事件，但不可對外接單、改 OwlNest 房況、觸發付款或成功通知；舊 Sheet 仍是唯一正式紀錄。OS 既有 `/api/v1/calendar/changes` 是寫入後通知，接收端會重讀 Sheet，**不能**當作訂單寫入 API。

平行期先**持久保存**郵件事件與識別，再執行舊表寫入／讀回，最後投遞影子事件。兩個目的地無法組成一筆跨系統交易，因此不能把「兩次 API 都呼叫成功」當成一致性的保證：舊表成功、影子失敗時，舊表營運照常，影子事件保留待重試且切換門檻不通過；舊表失敗時，不把該事件套進影子冒充已接單。服務中斷造成事件缺口時，還要用完整 Sheet 快照與 Gmail 事件紀錄補對。若影子收到修改／取消卻找不到原單，保留待核，不自動另建新單。

**切換後目標：**同一個受權 Gmail 服務解析郵件後，產生含館別、平台、外部訂單 ID、Gmail message ID、來源順序／版本、動作、完整原始房晚及私密證據參照的**持久事件**；透過僅限 Sweetfun 的服務憑證提交到 Iron Gate。Iron Gate 在同一館別的權威版本／房晚鎖下新增、改期／改房、取消並保存來源連結與冪等回執。服務讀回訂單 ID、版本、房晚、狀態及事件回執**確實相符**後，才把該郵件標記已完成或已讀、發成功通知；不確定結果查同一事件／請求鍵，不另造新單。原 Sheet 保留作歷史證據；如需報表，從 Iron Gate 單向輸出一份明確標記非權威的副本，絕不讓副本反向更新權威。

這不是目前已完成的串接。現有 Iron Gate `source:write` 有外部來源連結、來源版本及 `review_required` 概念，可作設計起點，但尚須核對它是否能完整承接 Gmail 的多房多夜、費用／付款、修改、取消與異常房晚。`review_required` 不能被 Gmail 當成成功並標記已讀；原始事件須安全保留供人工修復。若 OTA 本身有真實超賣，不能因 Iron Gate 拒絕占房就丟失通知；需保留訂單證據、封住相關房晚並發調查告警，同時避免假稱已成功接單。

切換所需的 Gmail 專項檢查：

1. **盤點實際入口。** 核對正式 Cloud Run revision、Watch／Pub/Sub、補收排程、郵件標籤、Firestore 處理 claim／訂單水位、LINE 或人工補單路徑、Sheet updater、Apps Script 觸發及通知；記錄哪個入口真正寫水芳表。另核對 `process_email` 的成功通知與郵件已讀時機。
2. **封裝寫入端。** 在現有解析器後建立明確 `legacy_sheet` 正式 sink、`iron_gate_shadow` 隔離影子 sink，以及切換後的 `iron_gate` 正式 sink；按館別和 authority epoch 路由。切換前只有舊表能正式寫，影子只接收可核對的副本；切換後只有 Iron Gate 能正式寫。開關在服務端拒絕舊代次，在途事件有明確排空／重派規則。不能只改 webhook，留下補收或手動路徑繼續寫 Sheet。
3. **事件身分與順序。** 用 Gmail message ID 防同封重播，用平台＋帳號＋訂單 ID 綁定同一張訂單；取消保留 tombstone，不因來源列被刪而忘記身分。現有修改郵件以 Firestore message claim 和郵件時間水位防舊改單覆蓋新單；新通道必須維持或加強此保護，時間戳相同／缺失／平台事件順序不明就待核對。對新單與取消也要有 durable event／回執，不能只倚賴 Sheet 當去重證據。
4. **未知結果與郵件狀態。** Pub/Sub 至少一次、重送、索引延遲與服務中斷均須測；提交逾時先讀同鍵回執。`已解析`、`已保存待核`、`已套用並讀回`、`需人工` 分開記錄；平行期以**舊表**寫入及讀回成功作郵件完成依據，影子失敗進獨立待補佇列，不阻斷原本營運；切換後才改以 **Iron Gate** 的權威回執作依據。已保存但撞房／缺 ID 的郵件進持久 review queue 和警報，不遺失；保留目前 24 小時補收，另做超過窗口的對帳與人工補收程序。
5. **逐案驗收。** 使用合成平台郵件驗新增、多夜多房、改日期、改房、重複通知、先取消後補新單、較舊改單、找不到原單、取消後重送、部分付款、超賣、Gmail 已讀／未讀轉換、Sheet／Iron Gate 任一端故障、切換瞬間在途事件及回退。比對來源信件數、持久事件數、已處理／待核數、Iron Gate 訂單與逐房晚、既有 Sheet 快照；沒有未說明落差才允許切換。

## Sean OS 與 LINE 入口的平行驗證

- **Sean OS 工作台：**逐個查原生建單、改期／取消、保留、封房、收款、退款、財務分錄及 H 欄回寫的實際 route、儲存層與讀回；不能只修改日曆畫面。舊權威操作驗證後送同 ID／版本的影子事件，影子不觸發通路寫入或通知。
- **LINE 官方帳號：**逐個查指令身份、業主確認、主表或 OS 訂單寫入、OwlNest 開房／關房及收款落點。LINE 財務須以 Firestore 原始 entry／version／operation／outbox 為核對起點，再對照雙 Sheet 專頁投影；摘要列不可再作一筆收入，未知投影結果不可再次登記收款。開關房需逐間逐晚比對 Iron Gate 占房與 OwlNest 實際庫存；影子期只模擬命令結果，**不向 OwlNest 再送一次**。改單與收款要保留原訂單及事件 ID，失敗或結果不明進待核，不能另建一筆或重複收款。
- **共同規則：**三個入口使用同一館別的來源 ID→正式訂單 UUID 對照和操作版本；來源已經互相改過的訂單不能被較舊的 Gmail 信或 LINE 指令覆蓋。每個入口分開統計收到、套用、待補、待核，並在切換時逐一證明舊路徑已被改接或拒寫。

## 執行順序與每一關的通過證據

### 0. 鎖定範圍與 writer 清單

盤點最新主表及所有相關財務分頁、Sheet 公式與表頭、歷史期間、六間房和任何包棟／改房語意；列出現在能新增／取消／改期／登記收款／退款／封房的入口：人工作業、**Gmail check order 的即時 webhook、補收、人工重跑與 Sheet updater**、**Sweetfun OS 工作台的訂單與財務儲存層**、**LINE 官方帳號的訂單／收款／OwlNest 指令**、H 欄回寫、網站、其他排程，以及客戶工作區測試副本。確認哪一份是訂單、房況、每種財務事實各自的權威，哪些是衍生快照。**通過證據：**有來源清單、來源涵蓋期間、三條入口與其他 writer 的開關表；不明入口不得進切換。

### 1. 擷取不變基線與可還原備份

以唯讀權限擷取原表**完整**內容、H 註記、相關財務分頁與表頭、公式／格式等需要保留的結構中繼資料、擷取時間與來源版本；保存在受控私密儲存並記雜湊、列數與權限。另備份 Sean OS 的訂單／收款／財務／待處理任務、LINE Firestore 分筆財務帳本及版本／操作回執／audit／outbox／投影水位、LINE 訂單財務 registry 的期初／刷卡來源與操作紀錄、Gmail 處理紀錄，以及 Iron Gate 資料庫。用隔離環境還原、重算雜湊、確認可讀；保留遷移期間後續增量快照。**通過證據：**備份與還原紀錄、版本／雜湊一致、原表再讀相同，原表沒有被寫入。

### 2. 完整轉換器與例外佇列

建立專用的 Sheet→標準訂單候選轉換器、來源 ID→UUID 對照、人工核對紀錄與冪等匯入批次；並定義 Gmail、OS、LINE 共用的訂單及財務事件識別／修改契約。對**每一來源列**逐 J 驗證、逐 L 分組；保留多段 `stays`，列出取消／刪列／改期差異；逐實體房晚計算占用。對**每一收退款、費用配置與沖銷事件**對照來源實有的事件 ID、金額、日期、付款方式、帳戶及訂單；原來源缺少的欄位保留未知並標示外部結算未驗證，不補造資料。再從目標反向逐筆找回來源，另以獨立計算重算房晚及總額，不能抽樣。來源問題以 fence／待核對標記。先補齊 Iron Gate 缺少的來源、財務與回讀欄位契約；經 migration 與測試證明可以無損往返，才允許真實資料進目標。現有 `createBooking` 和 `source:write` 不能直接代替歷史匯入：前者會新建訂單，後者是外部來源事件協定。**通過證據：**全量逐筆核對報告，加上合成多房連住、重複 J、空 L、改列位置、刪列、付款差異、撞房、重跑／中斷後重試和跨館隔離測試；未核對資料不得變為可售。

### 3. 隔離 Iron Gate 影子試轉

在**與正式 Iron Gate 分離**的受控資料庫，用第 1 步快照試轉；保留來源 ID、版本、映射與營運唯讀旗標。影子可透過受限遷移入口接收後續 Gmail 事件，但不啟用接單、通路庫存或通知。只輸出無客資報告，細節留在受限環境。**通過證據：**總來源列、已接受列、待核列、父單、取消／未知、逐房晚占用、逐單／逐月房費和收退款等可核對總額；對每一缺漏、額外、差異或撞房有原因與處置。已知 2026-10-16 的 8 列待核只是舊基線，不能自動批准或忽略。

### 4. 追上營運增量並平行唯讀觀察

原 Sheet、OS 財務帳本與現有通路操作維持各自已核實的正式權威。Gmail 服務將舊表**已核實**的新增／修改／取消送入隔離 Iron Gate 影子；OS 工作台與 LINE 的已核實訂單／房晚／收退款變動也產生來源事件供影子核對。人工改表、列移動、撤銷候選及財務任務以完整來源版本反覆擷取補對。來源不完整或讀取失敗時維持舊影子版本並標記落後。對照三入口持久事件／補收結果、Sean OS 日曆、訂單搜尋、財務帳本和 OwlNest 已觀測的房況；影子差異不改真實庫存。**通過證據：**連續觀察期涵蓋實際新增／修改／取消／收款／開關房與中斷恢復，對照各入口事件數、舊權威成功數、影子套用數、待核數及逐房晚／逐財務事件；每一差異都有原因與處置，沒有未解釋的漏單、重單、重複收款或可售房晚差異。若期間缺少某類真實案例，以合成事件另行演練，不能把「零事件」當成通過。最後影子水位與 Gmail／Sheet／OS／LINE 水位一致，未決房晚封住銷售。

### 5. 逐館切換前檢查與受控切換

先完成 OS、Gmail 與 LINE 服務對 Iron Gate 的授權讀取／寫入接線，並演練舊 writer 封寫、Iron Gate 受限角色、備份、回滾、監控與 API 回讀。安排水芳切換窗口：暫停 Gmail webhook／補收、OS 工作台、LINE 指令及其他新舊入口的競爭寫入，**保留 Pub/Sub／郵件與操作事件以便恢復**，等待在途 Sheet／OS／LINE／OwlNest／財務任務結清，取得最終快照和雜湊，在 transaction／版本閘門下匯入最終差額；逐單、逐房晚、逐筆收退款與來源版本讀回，再將該館 authority epoch 切到 Iron Gate，確認三入口唯一指向新權威後排放停窗事件並開放新 writer。隔離影子是驗證證據，**不能直接當成正式庫或跳過最後匯入與讀回**。任何檢查不通過，維持舊權威，Iron Gate 不接單。**通過證據：**業主確認的核對報告、正式備份還原演練、三入口路由／在途／補收檢查、所有舊入口封寫檢查、零未解釋重疊、逐房晚與逐財務事件對照及端到端新單／改期／取消／收退款／開關房回讀。通過後仍需單獨的正式切換授權。

切換後監看 Gmail 接收→持久事件→Iron Gate 回執→郵件完成的延遲與積壓、訂單／房晚／付款差異、來源落後、重試、OwlNest 對帳與警報。原 Sheet 保留作歷史證據；應清楚標記其已非新訂單正本，限制人工新寫入，但不刪改舊資料。預定觸發條件（漏信／漏單、錯房、重複收款、無法回讀、通路差異）一旦發生，先停止新接單並保護現有房晚；按已演練的差額回填與版本水位程序回退，不能同時重開兩個 writer。**通過證據：**觀察期對帳紀錄、事故處置／回退演練和業主驗收。

## 業主／PM 驗收時要看的三件事

1. **差異有沒有收斂。** 報表要同時列出 Gmail、OS、LINE 的操作數，舊權威與影子成功數、待補、待人工，以及逐房逐晚、收退款和金額差異。每一筆差異由工程端追查並記處置；不能只展示「兩套服務都在線上」。
2. **新操作看起來是否正確。** 業主在測試期只需抽看少數新進訂單、改單、LINE 開關房與登記收款是否符合日常認知。工程端自行完成**全部既有來源列與財務事件**的逐筆雙向核對；不請業主人工檢查每一列。只有資料無法判定的真實營運事實，才整理成少量清楚問題請業主決定。
3. **切換條件有沒有真的達成。** 看最後快照、備份還原演練、三入口全部停寫／排空、正式 Iron Gate 讀回、在途事件補處理及回退演練的證據。任何關鍵差異未解決，就延後切換；原 Sheet 保留，但不讓它與新系統同時獨立接新單。
